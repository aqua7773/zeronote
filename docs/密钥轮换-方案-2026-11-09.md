# 密钥轮换方案（换环 = 只换包裹层）

> 状态：**accepted**（用户 2026-11-09 拍板「用 B + 密码库也加中间层 + 一次操作」）
> 作用范围：`security` 的 crypto 服务 / `private-notes` / `secrets`
> 当前进度：**格式层已实现 + 6 条单测通过**（`examples/security/index.js` · `tests/crypto-itemkey.test.ts`）；
> 其余（服务方法 / 两个插件接入 / UI）未开始。

## 1 问题（为什么必须做）

用户删掉一把环、给插件分配新环之后，**插件完全解不开已有数据**。实测（Redmi dev 包，手机测试库）：

1. `grants.json` 里 `b → secrets`（分配确实生效）
2. `vault.b.json` 用主密码能解出 32 B DEK（密码没错）
3. 点「解锁」却显示「主密码不对」—— 真因是 `secrets.zn` 还是**旧环**加密的，新 DEK 解不开
   （`examples/secrets/index.js:1568` 把 `/invalid tag/` 一律翻译成「主密码不对」，误导了排查方向）

根因是密钥结构只有两层：

```
主密码 --(包裹)--> DEK --> 数据          数据段 AAD = "<环>|<容器>|data"（含环 id）
```

**换环 ⇒ 换 DEK ⇒ 所有密文失效**，且 AAD 绑死环 id，连"沿用同一把 DEK 只换环名"都做不到。

顺带暴露的两个产品缺口：

- 分配时不做校验：给"已有数据"的插件换环，等于让数据直接失效，没有任何提示。
- `private-notes` 是**一篇一个密文文件**，没有"整树重加密"的循环 ⇒ 换环后索引换了新环、正文还是旧环，一半迁一半死。

## 2 调研（其他产品怎么做）

| 产品 | 结构 | 换主密码时做什么 |
|---|---|---|
| Standard Notes | rootKey → itemsKey → item_key（每条数据一把） | 只重写 itemsKey（几 KB），数据不动；旧数据在**下次编辑时渐进重加密** |
| Cryptomator | password → masterKey → contentKey（每文件一把，存文件头 68 B） | 只重写每个文件的 header + 文件名，内容不重写 |

来源：[Standard Notes 白皮书](https://standardnotes.com/help/security/encryption)、
[Cryptomator Vault Cryptography](https://docs.cryptomator.org/security/vault/)

结论：主流产品都有一层 **per-item key**，换主密码只重写这一层小 key。ZeroNote 缺的就是这层。

## 3 设计

### 3.1 三层结构

```
主密码 --(argon2id)--> masterKey --(包裹)--> DEK --(包裹)--> itemKey --(加密)--> 数据
```

itemKey 每份数据一把（32 B 随机），**只以包裹形式存在**，插件永远拿不到明文（§9.4「消费者拿不到 DEK」不变）。

### 3.2 格式（已实现）

| 标记 | 形态 | 用途 |
|---|---|---|
| `zn1.<n>.<ct>` | 旧格式 | 只用 DEK 加密，**继续支持读**（渐进升级期的老数据） |
| `wk1.<n>.<ct>` | 包裹段 | DEK 包裹的 itemKey（AAD = `<环>\|key`） |
| `zn2.<n>.<ct>` | 数据段 | itemKey 加密的数据（AAD = `<容器>\|<作用域>`） |
| `zn2.<wn>.<wc>.<dn>.<dc>` | 自包含 | 包裹段 + 数据段在同一文件里（单文件插件用，如密码库） |

### 3.3 AAD 分工（这一层的全部要点）

- **包裹段 AAD 含环 id**：`<环>|key` ⇒ 换环必须重包，旧包裹块挂到新环下解不开。
- **数据段 AAD 不含环 id**：`<容器>|<作用域>` ⇒ 换环后正文照样能解。
  环的隔离由包裹段承担；这正是"只重包、不动正文"成立的前提。

### 3.4 换环 = 只重写包裹段

```
读文件 → 旧环 DEK 解出 itemKey → 新环 DEK 重包 → 数据段原样搬回 → 写盘
```

**全程不解密正文、不产生明文**。这是"换环不暴露数据"的关键。

### 3.5 存储位置（按插件形态选）

| 插件 | 形态 | itemKey 放哪 |
|---|---|---|
| `private-notes` | 多文件（一篇一个 `.zn`） | **索引** `.zn/private/index.zn` 的 `keys` 表（方案 B） |
| `secrets` | 单文件（`secrets.zn` 一个） | **文件头**（自包含 5 段格式，方案 A 的形态） |

选 B 的理由（用户已拍板）：换环只改一个文件。代价与缓解见 §7。

## 4 一次操作交互

用户只操作一次，后台按顺序执行。进入有两条路径：

**路径一（已有新环）**

```
┌─ 轮换密钥环 ──────────────────────┐
│ 把「私密笔记」 测试环A → 测试环B   │
│ 当前环密码 [••••]  新环密码 [••••] │
│ ℹ 正文不会解密，只重写包裹段（约 3 秒）│
│                  [取消] [开始轮换] │
└────────────────────────────────────┘
```

**路径二（没有新环）**：同一弹窗先填新环名称 + 密码 ×2，再加当前环密码，按钮 `[新建并轮换]`。

点了之后弹窗切成进度视图：

```
解锁旧环… ✓
解锁新环… ✓
重新打包 12 / 37
─────────────────
完成后自动锁定两把环
```

三条设计约定：

1. **成功后自动锁定两把环**（不让旧环留在内存里）。
2. **中途失败可重跑**：数据段没被碰过，失败的条目仍在旧环包裹下，两把环都在就能续跑。
3. **旧环不自动删**：轮换完成只提示「旧环现在可以删了」，删除要单独确认（可能是泄露取证材料）。

## 5 换环流程（服务层要求）

| 步骤 | 做什么 | 失败怎么办 |
|---|---|---|
| 1 | 解锁旧环（主密码 / 指纹） | 直接报错返回，不动数据 |
| 2 | 解锁新环（主密码） | 锁回旧环，不动数据 |
| 3 | 逐条重包（`rewrapKey` / `rewrapSelfContained`） | 记录失败条目，两把环保持解锁，可重跑 |
| 4 | 全部成功 → 写索引 / 写文件 → 锁两把环 | 任一条失败 ⇒ 不提交，回滚为"未轮换" |

## 7 风险与缓解

| 风险 | 缓解 |
|---|---|
| **索引单点**（选 B 的代价）：索引损坏 = 全树打不开 | 写索引前备份上一版 `index.zn.bak`；`loadIndex` 失败时提示从备份恢复 |
| 换环要求两把环同时解锁 | 一次操作弹窗内部依次解锁（§4）；失败时保持解锁可重跑 |
| 旧 zn1 数据在换环后解不开 | 换环前置校验：还有未升级的 zn1 条目 ⇒ 先提示「升级后再换环」，或自动全量升级 |
| 插件认新环不及时 | 沿用 rev173.443 的 `adoptRing()` 修复；换环命令内部先 `adoptRing()` |

## 8 验收点（G1 / G2）

**G1 自动化**

- `tests/crypto-itemkey.test.ts`：换环后新环能解 / 旧环解不开 / 数据段逐字节不变
- 新增轮换流程测试：失败条目重跑后能全部完成；中途失败不写坏索引

**G2 真机 / 桌面**

1. 建新环 → 分配 → 用旧环解锁 → 轮换 → 新环解锁能读全部数据（私密笔记篇数 / 密码库条目数一致）
2. 轮换期间断网 / 杀进程 → 重启后数据仍可读（旧环仍可用）
3. 轮换后用旧环解锁 ⇒ 旧密文仍能读（旧环未删时的安全网，符合 §3.4）
4. 磁盘明文扫描 0 命中（换环全程没有明文落盘）
