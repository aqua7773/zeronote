## 0 一句话结论

做成**两个纯 JS 插件**（不碰内核）：

- **`security`** —— 主密码 → **Argon2id** → 主密钥（只在内存）→ 每容器随机**数据密钥**用主密钥包裹 → 数据用 **XChaCha20-Poly1305** 加密；对外 `service.provide('crypto')` 给其他插件用。支持**多个密钥环**：`notes`（私密笔记）与 `secrets`（账号密码）**各一把主密码，互不派生**。
- **`secrets`** —— 绝密账号库（密码管理器），消费 `crypto` 服务，整库单独加密存 `.zn/secrets/secrets.zn`。

**生物识别另立期 2b** —— Tauri 官方 biometric 插件不支持 Windows，且上手机要重编 APK。

## 3 算法与参数（本机实测）

跑法：`_tmp-crypto-bench/bench.mjs`，Node v24.21 / Windows x64 / V8（桌面 WebView 同引擎）；每档 3 次取中位数。

**手机列已于 rev173.165（期 2a）实测填上**（真机 `33b676f6` · Redmi peridot · Android WebView V8 · 0.5.0 dev 包 · 三档各 3 次取中位数）。

| 档 | 桌面实测 | 手机实测（2026-10-26） | 备注 |
|---|---|---|---|
| Argon2id **t=2, m=19 MiB, p=1**（OWASP 最小档） | 212 ms | **165 ms**（226/165/162） | ⚠️ 手机比桌面**快**，不是慢 1–4× |
| Argon2id **t=3, m=64 MiB, p=1**（RFC 9106 推荐档） | 993 ms | **812 ms**（834/812/806） | 同上 |
| Argon2id t=1, m=128 MiB, p=1（官方 benchmark 同参） | 682 ms | **574 ms**（586/574/563） | 同上 |
| scrypt N=2^17, r=8, p=1（对照） | 452 ms | 未测（不采用） | — |
| XChaCha20-Poly1305 加密 1 MiB | 7.9 ms（≈130 MiB/s） | **29 ms**（≈35 MiB/s） | 手机慢 3.7×，但绝对值可忽略 |
| XChaCha20-Poly1305 加密 24 B（每次新 nonce） | 20.4 µs | 未单独测 | — |
| 包裹 32 B 数据密钥后的密文长度 | 48 B | — | 与平台无关 |

补充一组手机端配套数据（同一次实测）：
- **vendor 六个模块首次加载 114 ms**（之后走模块缓存为 0）
- 解密 1 MiB 7 ms
- ⇒ 手机首次解锁 ≈ **114 + 812 + 解密（密码库几 KB，可忽略）≈ 0.93 s**；之后 ≈ **0.81 s**

> ⚠️ **对上文的更正（rev173.165）**：本方案 §3 原先按 noble 官方说法估「手机 1–4× 慢，t=3 档 2–4 s」。
> 真机实测推翻了这条 —— 手机 Argon2id 反而比桌面 Node **快约 0.8×**（同一份实现、同为 V8）。
> 可能原因：手机 CPU（peridot）单核性能不低于测试机、且桌面那次跑在 Node 而非 WebView 里。
> 无论原因，**「手机慢到需要降档」这个前提不成立** ⇒ 下面的取档决定不动。

**取档决定（rev173.165 定死）**：默认 **t=3 / m=64 MiB**（RFC 9106 推荐档），**不退回** t=2 / 19 MiB ——
方案原先留的后路条件是「手机实测 > 5 s」，实测 0.81 s，条件不成立。理由：
- 手机上「解锁等 0.8–0.9 秒」是可接受量级（且必须**先渲染"正在派生密钥…"再算**，否则界面死 0.8 秒像卡死）；
- 参数写进 `vault.json` 的 `kdf` 段 ⇒ 以后调档不影响老数据（解密用存档参数，加密用新参数 + 重新包裹）。
- ⚠️ 这次测的是 **debug 包**（dev 前端未压缩）。release 包只影响解析阶段，对纯数值计算影响很小；
  真要抠，期 2b 重装 APK 时顺手复测一次即可。

**关于 Argon2 的两个诚实点**（写进文档与 UI 说明，不隐藏）：
1. noble 的 argon2 **未经 Cure53 审计**（README 明确排除）；xchacha 在审计范围内。
2. 官方建议用 Scrypt 替代（JS 里 Argon2 慢 5×，攻击者用 native 跑就更快）。**但需求 §9.3 点名 Argon2id**，本方案按需求走；切 Rust（方案 B）能消掉这条劣势。

**XChaCha 的选型理由**（官方 README 原文）：192-bit 随机 nonce ⇒ 无需计数器、碰撞概率可忽略，正合"本地随机 nonce、多设备各自加密"的场景；`managedNonce` 可自动把 nonce 前置进密文。

## 4 密钥层级与落盘

```
主密码（字符串，不落盘）
  └─ Argon2id(salt 16B, t=3, m=64MiB, p=1) ──→ masterKey(32B, 仅内存)
                                                 │
        每个加密容器（containerId 由调用方给，例如 "vault:<库名>"）：
          DEK = randomBytes(32)  ──XChaCha(masterKey, nonce24, aad=containerId)──→ wrapped(48B) 落盘
          data ──XChaCha(DEK, nonce24, aad="<containerId>|<field>")──→ zn1.<nonce>.<ct> 落盘
```

- **不存 password verifier**：解锁 = 拿 masterKey 去解任一个 `wrapped` DEK，AEAD 认证通过即密码正确。少一份可离线爆破的校验值（`wrapped` 本身同理，但少了"密码哈希"这一层）。
- **AAD 绑定容器**：把 `containerId` 作为附加认证数据 ⇒ 把 A 容器的密文搬到 B 容器下会**解密失败**，不是静默串数据。
- **换主密码**（= 需求 §9.3 的"恢复"语义）：解出所有 DEK → 新 masterKey → 重新包裹 → 数据密文**一个字节都不动**。
- 密文格式自描述：`zn1.<b64url nonce>.<b64url ciphertext+tag>`，将来换算法就换 `zn1` 前缀。

**落盘位置：库内 `<库>/.zn/security/vault.json`**（`fs.writeText` 原子写）：

```json
{
  "v": 1,
  "kdf": { "algo": "argon2id", "t": 3, "m": 65536, "p": 1, "salt": "b64…" },
  "containers": { "vault:默认": { "wrapped": "zn1.…", "createdAt": 1793… } },
  "recovery": { "question": "…", "answer": "zn1.…", "salt": "b64…" }
}
```

为什么按库而不是全局：`fs` / `store` 都按库隔离（D-004），插件**没有**写库外的通道（`host.saveFile` 是用户选位置）；且同步时 `salt` + `wrapped DEK` 跟库一起走，换设备输主密码即可解开 —— 正好是 §10.1「加密后同步」需要的前提。
⚠️ 主密码是**每个密钥环各一把**（见 §4.5），不是"一个库一把"。

## 4.5 绝密账号库（密码库）

> **2026-10-25 用户拍板**：① 放 `.zn/secrets/`（同步插件放行）② 恢复 = 安全问题 + 恢复码双路径 ③ **密码库主密码与私密文件夹分开** —— 原话「私密文件夹只是一些非公开个人笔记，账户密码要保证绝对安全」。

### 双密钥环（每个环独立）

| 密钥环 | 主密码 | 容器 id | 保护对象 | 空闲锁定 | KDF |
|---|---|---|---|---|---|
| `notes` | **A** | `private` | 私密笔记 | 3 分钟 | Argon2id t=3 / m=64MiB |
| `secrets` | **B** | `secrets` | 账号密码 | **60 秒** | 同上，**不共用 salt** |

硬隔离（三条都不共享）：独立 `salt` · 独立 DEK · 独立恢复问题与恢复码。密码 B 不能由 A 推导，泄露或忘记一个环不影响另一个。

### 落盘

```
<库>/.zn/security/vault.json    ← 两个环的 KDF 参数 + wrapped DEK（文件里没有任何密钥）
<库>/.zn/secrets/secrets.zn     ← 密码库整库密文，AAD = "secrets|v1|<库 id>"
```

```json
{
  "v": 1,
  "rings": {
    "notes":   { "kdf": { "argon2id": { "t": 3, "m": 65536, "p": 1, "salt": "b64" } },
                 "wrapped": { "private": "zn1.…" },
                 "idleLockMs": 180000 },
    "secrets": { "kdf": { "argon2id": { "t": 3, "m": 65536, "p": 1, "salt": "b64-另一个" } },
                 "wrapped": { "secrets": "zn1.…" },
                 "recovery": { "question": "…", "answerHash": "zn1.…", "wrap": "zn1.…" },
                 "recoveryCodeHash": "zn1.…", "codeWrap": "zn1.…",
                 "idleLockMs": 60000 }
  }
}
```

### 解密后的数据结构（只在内存）

```json
{ "v": 1, "updatedAt": 1793000000000,
  "platforms": [ { "id": "01J…", "name": "GitHub", "site": "github.com",
    "accounts": [ { "id": "01J…", "account": "aqua@x.com", "password": "…", "note": "",
                    "createdAt": 0, "updatedAt": 0, "deletedAt": null } ] } ] }
```

### 三条内存规则

1. **整库一次加密**，密码字段不再单独加密（多一层只会多一条绕过路径）。
2. **明文不出解锁期**：列表只返回 `平台名 / 账号 / 备注`，取密码是单独一次请求 —— 恶意插件"顺手读"只能拿到当前屏幕那几条。
3. **绝不进内核索引**：不调 `index.write`、不写 `.md`、不写临时文件。一旦进索引，明文就落盘了。

### 恢复（双路径，DEK 双重包裹）

```
DEK ──被主密钥包裹──→ rings.secrets.wrapped          平时解锁
DEK ──被恢复密钥包裹─→ recovery.wrap                安全问题答对时
DEK ──被恢复码密钥包裹→ codeWrap                     恢复码输入时
```

- 安全问题答案：先 `trim()` + 转小写再 Argon2id（需求要求宽松匹配）。
- 恢复码：24 字符 base32，**只显示一次**，建议打印保存。
- 两条路径都只做「重新包裹」—— **数据密文一个字节都不动**。

### 同步

- 同步 `secrets.zn` + `vault.json`（前者是密文，后者只有公开参数与密文块）⇒ 云端零明文。
- 冲突：两份密文都能用同一个 DEK 解开 ⇒ 保留两份让用户选（与笔记冲突副本同策略）。
- ⚠️ **必须先解决**：现有同步插件把 `.zn/` 整段排除（[folder.cjs](../examples/sync/lib/backends/folder.cjs)）⇒ 密码库在 `.zn/secrets/` 下**永远同步不出去**。要给四个同步后端各加一条白名单放行 `.zn/secrets/`（约 0.5 天）。

### 剪贴板与回收站

- 复制密码 → 60 秒后只在「剪贴板内容仍是这个密码」时清空（否则误删用户后复制的东西）。
- Android 10+ 后台禁读写剪贴板 ⇒ 定时器在后台失效，退化为「下次打开密码库时清空」。
- 回收站 = `deletedAt` 软删除（仍在密文里），启动时清理超过 7 天的；进入回收站要求重新验证身份。
- 可选更严：每次**查看**（不只是解密）都要求再次确认；`secrets` 环 60 秒无操作即锁。

### 与"绝对安全"的距离（写进 UI 说明，不夸大）

- **做到**：密码 A/B 分离 · 密钥分离 · 60 秒窗口 · 可恢复 · 云端零明文 · 换设备需重输密码。
- **做不到**：明文仍在 JS 内存（无沙箱，恶意插件可读当前查看的几条）· 密码输入在 JS 层 · 钓鱼框无法从技术上区分。

## 5 插件形态与接口

| 项 | 值 |
|---|---|
| id / 名称 / 分类 | `security` / 安全 / `tool`（`manifest.category`） |
| 平台 | desktop / android |
| 能力自述 | `fs:read` `fs:write` `command` `view:statusbar` `view:modal` `service` `event` |
| 目录 | `examples/security/`（当时预装插件走 `BUILTIN_PLUGINS` 登记；⚠️ rev173.259 起应用不预装任何插件，本行只剩历史） |

**服务（给其他插件用，需求 §9.4）**

```js
api.service.provide('crypto', () => ({
  isUnlocked(),
  unlock(password),            // 首次：生成 salt + 建容器；后续：验证并解包
  lock(),                      // 清 masterKey / 所有 DEK，发 security:locked
  encrypt(containerId, data),  // string | Uint8Array → "zn1.…"
  decrypt(containerId, payload),
  sign(containerId, bytes),    // HKDF(DEK,"sign") → HMAC-SHA256
  verify(containerId, bytes, sig),
  onChange(cb),                // 锁定/解锁回调（供私密文件夹做遮罩）
}), { version: '1.0.0' })
```

**UI 与命令**

- 状态栏（`location:'statusbar'`）：🔒 未解锁 / 🔓 已解锁，点开进 modal
- modal（`location:'modal'`）：设置主密码（两次输入）· 解锁 · 换主密码 · 设置/重置安全问题
- 命令：`security.setup` / `security.unlock` / `security.lock` / `security.change-password` / `security.recovery`

**自动锁定（需求 §9.2）**

- 每次 `encrypt/decrypt` 与 UI 操作刷新 `lastActive`；
- `setInterval(30s)` 检查 `now - lastActive > 3min` ⇒ `lock()`；
- `document.visibilitychange`（隐藏时记时间戳）+ 回到前台时**先用时间戳判定再决定是否立刻锁** —— 因为 Android WebView 在后台会**冻结定时器**，只靠 `setInterval` 会漏锁。
- 遮罩与"自动弹验证"：期 1 由消费者插件（私密文件夹）用 `onChange` 画遮罩；期 2 接生物识别后自动弹。

## 6 诚实边界（必须同时写进用户可见的说明）

1. **同上下文插件能读到密钥内存**：契约 §4 明说无沙箱，`window.__TAURI_INTERNALS__.invoke` 也在手边。所以本插件防的是**落盘泄漏与云端泄漏**，不是"防本机恶意插件"。要后者的前提是沙箱（D-001 已否决）。
2. **JS 无法保证擦除**：Uint8Array 可以 `fill(0)`，但 JS 字符串（密码）不可覆盖、GC 副本时机不可控（noble README §Memory dumping 也是这么说的）。文档里不写"已清零"，只写"尽力清空"。
3. **Argon2 未审计 + JS 慢**（见 §3）。
4. **解锁期间界面会停顿**（无 Worker）：用"先渲染提示再算"缓解，手机 2–4 s。

## 7 备选方案 B：把加密放进 Rust 内核

  > 不防同用户下的恶意进程（与 §8.5 的 Windows 边界一致）。
- **Windows**：~~官方插件不支持。两条路：① 自写 `UserConsentVerifier` ② 降级为主密码~~
  > ⚠️ **2026-10-26（rev173.167）实测更正 —— 上面这条写错了两处**：
  >
  > 1. **「不支持」只是 Tauri 插件层面**，Windows 平台自己有完整 API。而且**PIN 与生物识别是同一套**：
  >    `KeyCredentialManager` 只知道「Hello 凭据」，弹 PIN 还是指纹由 Windows 按用户设置决定 ⇒
  >    **「先做 PIN」不是降级，就是完整实现**；用户以后在系统设置里加个指纹，代码零改动。
  > 2. **`UserConsentVerifier` 这条路不够**：它只回 `Verified / NotVerified`，**不给任何密钥材料**，
  >    顶多算"二次确认"，不能当解锁凭证。真正能用的是 **`KeyCredentialManager`**：
  >    建 TPM 保护的 RSA 密钥对（私钥不可导出）→ `RequestSignAsync`（每次触发 Hello）→
  >    签名是确定性的（RSA-PKCS1 v1.5 + SHA256，官方文档明确这两项）⇒ `KEK = HKDF(sig)` → 用它包裹 DEK。
  >
  > **本机实测结论（PowerShell 5.1 直调 WinRT，同一台机器）**：
  > | 步骤 | 结果 |
  > |---|---|
  > | `IsSupportedAsync()` | **True**（PIN 已设） |
  > | `RequestCreateAsync(accountId, …)` | **Success** —— 非打包进程、无 HWND 也能建凭据 |
  > | `RequestSignAsync(buf)` | ❌ **90 秒无返回**（挂死）—— 签名必须有窗口 |
  >
  > ⇒ 实现门槛收敛成一条：**Rust 侧要用 `IKeyCredentialManagerInterop` 把 HWND 传进去**
  > （桌面 Win32 应用调 WinRT 异步 UI 操作的标准做法），Tauri 窗口句柄现成可取。
  > 另：签名确定性这次没测成（卡在挂死），依据是算法本身（PKCS#1 v1.5 无随机数）+ 官方文档写明的
  > SHA256/PKCS1；**实现时第一件事就是复测**（签名两次逐字节比对）。
- 期 1 的接口先留位：`unlock()` 之外允许后续加 `unlockWithBiometric()`，`vault.json` 预留 `biometric` 段（现在不写）。

### 8.5 Windows Hello 的具体设计（2026-10-26 定）

第三条包裹路径，与主密码 / 恢复码并列（复用现有 `wrapDek` / `unwrapDek`）：

```
DEK ──被主密钥包裹──────→ rings.secrets.wrapped.secrets     （主密码，现有）
DEK ──被恢复密钥包裹────→ recovery.wrap / codeWrap          （恢复，现有）
DEK ──被 Hello-KEK 包裹─→ rings.secrets.hello.wrapped       （新增）
                            ↑
Hello 签名 ──HKDF-SHA256(salt, "zn-hello-kek")──→ KEK(32B)
```

- **Rust 三个命令**（都 `cfg(windows)`）：`hello_available` · `hello_enroll(accountId)` · `hello_sign(accountId, message)`
- `accountId` 形如 `ZeroNote:<ringId>`（同一 Windows 用户下多个环各自一把）
- **失败语义**：`KeyCredentialStatus::NotFound`（用户重置过 PIN）⇒ 该路径失效，
  提示"用主密码解锁后重新绑定"；`UserCanceled` ⇒ 什么都不做
- **安全边界（必须写进 UI 说明）**：防的是**拿到磁盘 / 云端的离线攻击**与物理接近；
  **不防同用户下的恶意进程** —— 它也能发起签名请求，只是每次都要用户点确认。
  （这正是 Bitwarden 2024 年那次的教训：他们当时用 DPAPI 存解锁密钥，DPAPI **不绑定生物识别**，
  同用户任意进程 `CredEnumerateW` 直接掏走、连提示都没有 —— CVE-2023-27706；后来改用
  `KeyCredentialManager` 才修好。我们用后者，从一开始就走对的那条。）
- ⚠️ **主密码必须至少输过一次**：Hello 只包裹 DEK，不替代"能不能建库"。这样两把钥匙都有，
  丢一把不影响另一把。

### 13.2 块 1 · 内核 `service` 带调用方身份（契约改一处，向后兼容）

```ts
// src/kernel/contract.ts · ServiceApi
provide<T>(
  name: string,
  factory: (ctx: { caller: string }) => T | Promise<T>,   // 新增 ctx；现有 provider 可忽略
  opts?: { version?: string; perCaller?: boolean },        // 新增 perCaller
): Disposable
consume<T = unknown>(name: string): Promise<T | null>      // 签名不变，内核自动填 caller
```

- `caller` 来源 = `scoped(pluginId)` 的 pluginId；内核自身是 `'kernel'`。插件**无法伪造**。
- **默认语义完全不变**：全局一份实例、懒工厂、错误不外抛、并发只跑一次。只是 factory 多收一个对象参数。
- `perCaller: true` ⇒ 每个 caller 各跑一次工厂、各自缓存（错误也按 caller 记，坏的调用方不污染别人）。
- 改动点：`service.ts` 的 `Entry`（+`perCaller` / `values: Map` / `pendingByCaller` / `errorByCaller`）、
  `consume` 分两路、`provide` 登记 `perCaller`；`contract.ts` 的 `ServiceApi` 与 `service` 段说明。
- 单测 +6：默认跨 caller 共享同一实例 / `perCaller` 各跑一次 / 同 caller 复用 / 工厂抛错只该 caller 拿 `null` /
  `'kernel'` 也是合法 caller / 并发 consume 只跑一次。
- 向后兼容：旧内核上的新插件、新内核上的旧插件都能跑 —— 新字段可选，旧插件 factory 忽略入参。

### 13.3 块 2 · 环分配（A 方案）

`security` 改为按调用方出对象：

```js
api.service.provide('crypto', ({ caller }) => makeCryptoApi(caller), {
  version: '2.0.0',
  perCaller: true,
})

function assertRing(caller, ring) {
  if (granted(caller, ring)) return
  recordRequest(caller, ring)              // 记进 requested，刷新面板
  throw new Error(`插件「${caller}」未获授权使用密钥环「${ring}」`)
}
```

> v1 = 插件申请「具体某个环」、面板按**插件**一行勾选。新模型：插件只声明「我需要一个密钥环」

> （一个环只给一个插件、一个插件只拿一个环），环允许**未分配**；未分配时抛
> 「插件「X」还没分配到密钥环 —— 去「安全 → 密钥环分配」给它分配一个」。
> 新表：`{ "v": 2, "rings": { "notes": "private-notes" }, "demand": { "secrets": true } }`；
> **v1 不迁移**（当空表，用户重新分配一次 —— 用户 2026-11-07 拍板）。
> 实现 `examples/security/index.js` · 单测 `tests/security-grants.test.ts` · 交接 rev173.416。

  内存里 grant 变更不需重跑工厂 / 面板一键授权写盘。

### 13.4 块 3 · 统一指纹（设备级解锁密钥 DK）

问题：现在是「每环各绑一次」。底层 Android 同一把 Keystore 密钥、Windows 每环一个账号 —— 重复劳动。

**设计：引入设备级 `DK`（device key），环的 DEK 用 DK 包裹。**

```
首次绑定（一次 fresh 指纹 / Hello）：
  DK = randomBytes(32)
  wrapped = adapter.seal(DK, 'device')
  → .zn/security/device.<deviceId>.json  { v: 1, platform, wrapped, at }

每个环（新建时自动，零额外认证）：
  rings.<ringId>.deviceWrapped = wrapDk(libs, DK, ringId, DEK)   // AAD = "<ringId>|device"

指纹解锁任一环：
  DK  = adapter.open(device.<id>.wrapped)     ← 一次 fresh 认证
  DEK = unwrapDk(libs, DK, ringId, ring.deviceWrapped)
  · DK 缓存在内存（只要还有环处于解锁态）；清空时机 = 最后一个环锁定
```

- **建环继承**：DK 在内存 ⇒ 建环时立即写该环 `deviceWrapped`；DK 不在 ⇒ 首次指纹解锁该环时补写（一次认证继续可用）。
- **一次认证解多环**：DK 缓存在内存期间，解第二个环不再弹指纹。
- **兼容**：旧 `rings.<id>.biometrics.<deviceId>` 继续读；指纹成功解锁后写新段并删旧段（双读一个版本）。
- **解除**：`unbindDevice()` = 删 `device.<id>.json` + 本机所有环的 `deviceWrapped`（不再一个环一个按钮）。
- **落盘位置**：`.zn/security/device.<deviceId>.json`，**不加进** `PRIVATE_FILES`（本机凭据，别的设备解不了、也没必要搬）；
  `examples/backup/index.js:61-63` 只收 `vault.*.json`，本机绑定不备份 —— 符合语义，不改。
- 纯函数新增 `wrapDk` / `unwrapDk`（复用 `seal` / `open`），测试注入假适配器，不需要真机。
- 测试 +6：绑 DK → 两环各解一次只调一次 `adapter.open` / 建环时自动写 `deviceWrapped` /
  旧格式仍可解并迁移 / 解除后 `device.<id>.json` 与所有环旧段消失 / DK 清空后再指纹解锁要重新认证 / 别的设备槽一个字节不动。

### 13.5 块 4 · 依赖关系

- **已具备**（不动）：两个消费者已声明 `dependencies: ["security"]`；内核语义是「只提示、不排序、不拦加载」。

- 安全插件**不做**自己的弹窗入口（rev173.411 已定，不动）。

### 13.6 风险与诚实边界

1. **DK 削弱环隔离**：一次认证解出 DK 后，本机所有已授权环都能解 —— 这是「统一指纹」的代价。fresh 认证仍在（每次新会话要一次），但环与环之间不再各自一道生物门槛。写进面板说明。
2. **授权表不同步**：换设备要重新授权。这是有意的（本机策略），写进面板说明。
3. **无沙箱**（D-001）：恶意插件可以自己 `provide('crypto')` 覆盖、也能读盘。本层防的是「顺手读取」，不防恶意（与 §6.1 一致）。
4. **`crypto` 版本跃迁**：`1.0.0 → 2.0.0`，消费者已用 `consume` 软依赖，无需改调用签名（方法参数不变，只多一层授权）。
