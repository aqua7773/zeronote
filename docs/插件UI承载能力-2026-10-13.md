# ZeroNote 插件 UI 承载能力盘点 + 内核增强方案（2026-10-13）

> **这份文档回答一个问题**：内核现在给插件的 UI 能力，够不够承载"像参考产品那样的插件"？
> 不够的话缺哪几样、怎么补、按什么顺序补。
>
> **起因**：`examples/outline-map`（大纲 ⇄ 思维导图）按用户给的参考图做下去，撞到了内核的墙 ——
> 参考产品（幕布那类）的导图是**从笔记里弹出来的独立窗口**（可拖动 / 全屏 / 分屏 / **多开** / **可编辑并写回笔记**），
> 而 ZeroNote 的插件 UI 只有"宿主指定位置的声明式面板"。
>
> **用户 2026-10-13 的要求**（原话）：「内核允许增强能力，顺便检查内核现有能力是不是还会出现这种无法承载
> 插件功能的情况，**先完善内核，再做插件**」＋「或者插件完全是独立，只是数据和笔记同步是否可行」。
>
> 同日前一份盘点（`docs/插件能力盘点-2026-10-12.md`）覆盖的是**权限 / 分发 / 沙箱 / 生命周期**维度，
> 本文档**只覆盖 UI 承载能力**，两份不重复。

## §1 内核现在能给插件的 UI（事实 + 代码位置）

### 1.1 十一个原语（契约 §1 / §2；`src/kernel/contract.ts`）

| 原语 | 与 UI 相关的部分 |
|---|---|
| `fs` | 文件读写（含 `listDirs`/回收站四命令，见 rev38/rev40） |
| `doc` | `active`/`open`/`close`/`save`/`selection`/`replaceSelection`/`insertAtCursor`/**`insertAt(pos,text,cursorOffset)`**/`on(...)` |
| `index` | 全文索引查询 |
| `event` | 进程内事件总线 `on`/`emit` |
| `command` | `register`/`bind`（可接管 `core.*`）/`execute`/`list` |
| `view` | `registerPanel`（声明式面板）/`registerWebView`（iframe）/`refresh`/`setState` |
| `store` | 插件私有 KV |
| `host` | `log`/`notify`/`assetUrl`/`saveFile` |
| `editor` | `addMark`（编辑器行内标记规则，声明式） |
| `service` | 懒工厂 + 软依赖 |
| `kernel` | 元信息 |

### 1.2 声明式 UI：UINode 21 种（`contract.ts:250-330`）

`stack` `row` `divider` `spacer` `text` `markdown` `code` `html` `link` `image` `button` `input` `textarea`
`select` `checkbox` `list` `table` `progress` `badge` `field` `tabs`

特征：宿主渲染 ⇒ **外观 100% 统一**，但**表达力到此为止**（无画布、无拖拽、无富菜单、无自绘）。

### 1.3 面板位置：五种，全部由宿主决定（`contract.ts:341-355`）

`main`（主区整页）· `modal`（弹窗，复用设置页 Dialog 原语，`App.tsx:2590`）· `statusbar` ·
`editor-toolbar` · `editor-topbar`

⇒ 插件**不能自己开窗口**，也不能决定"这个面板是可拖动的浮窗"。

### 1.4 逃生口：`registerWebView`（iframe）

有主题令牌注入 + `sandbox="allow-scripts"` + CSP 白名单（契约 §2.2，`WebViewFrame.tsx`）。
**但**：① iframe 只能"收"令牌，**不能调 `ctx.*`**（10-12 盘点 G6 未做）；
② **Android 上 `http://asset.localhost/...html` 返回 `ERR_INVALID_RESPONSE`**（rev30 实测）⇒ 移动端不可用。

## §2 三条系统性缺口

> 结论：这次不是"缺某一个 UINode"，而是**三个能力维度整体缺失**。
> 任何"工具窗口型 / 富交互 / 结构化编辑"的插件都会撞同一面墙。

| # | 缺口 | 证据 | 影响面 |
|---|---|---|---|
| **U1** | **插件不能自己开窗口** —— 位置、尺寸、是否可拖动全部由宿主写死 | `ViewApi` 只有 `registerPanel`/`registerWebView`/`refresh`/`setState`（`contract.ts:358-404`）；`PanelLocation` 是封闭枚举（`contract.ts:341-355`） | 导图窗口、画布、看板、参考预览、日志窗 |
| **U2** | **没有自定义渲染入口** —— 声明式表达不了节点拖拽 / 富菜单 / 画布；iframe 那条路在 Android 不通 | UINode 21 种（§1.2）；rev30 的 Android asset 结论（§1.4） | 所有富交互插件 |
| **U3** ✅ **已修（rev45，2026-10-13）** | **改不了笔记的任意区间；而且订阅是空桩** | ① `doc` 有 `insertAt`/`replaceSelection`，**没有** `replaceRange`（删不掉已有内容）；② `App.tsx:623` 是 `on: () => ({ dispose: () => {} })` —— 契约 §1.2 声明的 `doc.on('open'\|'change'\|'save'\|'close')` **永远不触发** | 导图↔大纲双向同步、表格单元格编辑、任务勾选回写 |

**U3 的第二条尤其阴**：它不报错、不警告，插件订阅了文档变化就是**收不到**（"静默失效比报错危险"）。

## §3 用户 2026-10-13 的裁决（改变了架构边界）

| 裁决 | 含义 |
|---|---|
| **「不需要防『插件把界面改成任意样子』」** | 放弃"**声明式 UINode 唯一主路**"这条防线 —— 契约 §2.6/§7 一直在守它（也是 10-12 盘点里的"领先项 L1"）。**U2 获批** |
| **「只是同一套设计风格就行」** | 视觉一致性由**内核提供 token + 一套 class**、插件自觉遵循；不再靠"只能声明式"来保证 |
| **「况且现在是自用阶段」** | 不为第三方插件市场做安全防护（沙箱仍搁置，见 10-12 盘点 G1） |

⇒ **内核可以给插件：真窗口 + DOM 挂载点**。代价是插件能自绘 UI，内核不再能保证外观统一。

## §4 增强方案（U3 → U1 → U2，按"通用性 × 成本"排序）

### U3a · `doc.replaceRange`（✅ **已完成** · rev45，2026-10-13）

**契约**（`contract.ts` DocApi，放在 `insertAt` 之后）：
```ts
/**
 * 按**区间**替换正文；`text === ''` 即删除。
 * `insertAt` 只能插、`replaceSelection` 只作用于选区 —— 结构化编辑（导图↔大纲、
 * 表格单元格、任务勾选）需要"改掉任意一段已有内容"。
 * 偏移一律夹进 `[0, doc.length]`（与 `insertAt` 同一套宽容策略）。
 */
replaceRange(from: number, to: number, text: string, cursorOffset?: number): void
```

**实现**（`App.tsx`，照 `insertAt` 的写法，`App.tsx:611-622`）：
```ts
replaceRange: (from, to, text, cursorOffset) => {
  const v = editorRef.current
  if (!v) return
  const len = v.state.doc.length
  const a = Math.min(Math.max(Math.min(from, to), 0), len)
  const b = Math.min(Math.max(Math.max(from, to), 0), len)
  const caret = a + Math.min(Math.max(cursorOffset ?? text.length, 0), text.length)
  v.dispatch({ changes: { from: a, to: b, insert: text }, selection: { anchor: caret } })
  v.focus()
},
```

**验收**（✅ 已按此做完，2026-10-13）：`examples/` 加了一个最小验证插件 `doc-edit-probe/`（夹具）：
跑 `node tools/cdp.mjs` 驱动命令面板执行它的命令，**以磁盘笔记为真源**断言 ——
全量替换后正文逐字节等于基准文本；中间区间替换后与旧文的**共同前缀 37 / 共同后缀 22**
（长度 62→62）⇒ **只有 3 个字符被改，其余一字未动**。

**实测契约**（落地版，比上面的草案多了两处宽容）：
`from`/`to` **顺序颠倒自动交换**、两端夹进 `[0, doc.length]`、`cursorOffset` 缺省 = 新内容末尾。

### U3b · 把 `doc.on` 从空桩接上真事件（✅ **已完成** · rev45，同一批）

**原来的现状**：`App.tsx:623` —— `on: () => ({ dispose: () => {} })`。
**落地实现**（rev45）：App 侧订阅表（`docSubsRef`，放 ref 因为 `docApi` 的 `useMemo` 依赖是 `[]`），四处 fire：
`openNote` → `'open'` · `onEditorChange` → `'change'` · `saveNow` → `'save'` · `closeNote` → `'close'`
（另：`docApi.close()` 也广播 close，与 `closeNote` 同一套语义）。
**决策（已定，2026-10-13）**：`change` 走 **trailing 去抖 200ms**（`DOC_CHANGE_DEBOUNCE_MS`）。
选它的理由：低于自动保存的 800ms ⇒ 顺序稳定（插件先见 change、后见 save）；再短（<150ms）在连续打字时
几乎等于每键一次；**不区分"结构性变更"** —— 内核不解析 Markdown，硬分就得把判据塞进内核，违背"内核保持薄"。
**两个实现要点（都来自实测，别再走回头路）**：
① **快照显式传参**：`open`/`save`/`change` 都发生在 `setContent`/`setActivePath` **之后**，
而 ref 是在 effect 里同步的 ⇒ 那一刻读 ref 会广播**旧文档**；所以 `fireDoc(ev, path, content, dirty)` 由调用方给快照。
② **切笔记/关笔记先兑现挂起的 change**（`flushDocChange`）：否则 `change(旧)` 会落在 `open(新)` 之后（乱序）。
**实测事件序列**：`open → change(dirty) → save(落盘)`；打字后切笔记 `change(旧) → save(旧) → open(新)`；关笔记 `close(path 正确)`。

**已知边界（写进契约 §1.2）**：`replaceRange` / `insertAt` 作用于**挂载中的编辑器**；
主区被插件面板占满时编辑器已卸载 ⇒ 调用是**静默 no-op**。U1 落地后这条边界才消失。

### U1 · `host.openWindow` / 真窗口（中）

**两条路**（用户已授权增强，建议 (甲)）：

| 路径 | 做法 | 能拿到 | 代价 |
|---|---|---|---|
| **(甲) Tauri 原生窗口（推荐）** | 前端用 `@tauri-apps/api/webviewWindow` 的 `new WebviewWindow(label, { url })` 开真窗口 | **拖动 / 全屏 / 多开 / 分屏全部天然满足** | ① capability 要放行新窗口标识（现在 `capabilities/default.json` 是 `"windows": ["main"]`）② 前端要有"窗口模式"入口 |
| (乙) 宿主内浮窗 | 内核把 `modal` 升级成可拖动 + 多实例 | 拖动、多开可做；**真全屏 / 拖出主窗口做不到** | Dialog → 窗口管理器 |

**(甲) 的关键设计**（下次直接照这个做）：
1. **窗口模式入口**：前端读 URL 参数（**已有先例**：`?vault=` 切库，见 HANDOFF「改 `devUrl` 加 `?vault=`」）
   —— 约定 `?pluginWindow=<panelId>&group=<key>` ⇒ `App` 检测到后**只渲染该插件的窗口内容**，不渲染侧栏/编辑器
2. **capability**：`capabilities/default.json` 的 `windows` 加窗口 label 模式（如 `"plugin-*"`）
   ⚠️ **这是安全边界变更** —— 虽已获"自用阶段"授权，落地时仍要在 HANDOFF 写明新增了什么权限
3. **窗口内容**：见 U2

### U2 · `view.registerWindowContent` / DOM 挂载点（中）

**契约草案**（`ViewApi`）：
```ts
/**
 * 注册一个**真窗口**，并把一块真实 DOM 交给插件自绘。
 * ⚠️ 这是 2026-10-13 用户裁决后的**有意开口**：放弃"声明式唯一主路"，
 * 换取富交互能力。插件自绘时必须用内核 token（`var(--zn-*)`）与 `.zn-ui-*`
 * class 保持同一套设计风格。
 */
registerWindow(spec: {
  id: string
  title: string
  /** 缺省 900×700；用户可自由拖动/缩放/全屏 */
  size?: { width: number; height: number }
  /** 打开窗口的命令 id（内核会为它注册一条命令 + 菜单项） */
  mount: (el: HTMLElement, ctx: PluginContext) => void | Disposable
}): Disposable
```
**落点**：`plugin-host.ts`（登记 + 卸载回收）· `App.tsx`（窗口模式渲染分支）· `WebViewFrame` 无关（不走 iframe）。
**风格一致性**：挂载点外层由内核挂 `.zn-window-body`（含 `--zn-*` 变量与基础字体/背景）；
插件用 token 自绘即与主题一致；再提供 `.zn-ui-*` 现成 class 给按钮/输入等常用件。

## §6 顺序、验收与风险

**建议顺序**：~~U3a + U3b（同一批，1 小时内）~~ ✅ **已完成（rev45，2026-10-13）** →
**U1（含 capability）← 下一步** → U2 → 插件重做 → 打磨（编辑/样式/菜单）。

**验收手段**：本会话已经把 GUI 验收从"截图+算坐标点鼠标"换成 **CDP**（`tools/cdp.mjs` + `dev.cmd` 的
`--remote-debugging-port=9222`，见 rev42/rev43）—— **内核增强的每一条都用它验**，不碰用户鼠标。

**风险**：
1. **声明式主路被放弃** ⇒ 从此"外观统一"靠自觉 + token，不再由架构保证（用户已知情并接受）。
2. **capability 放行新窗口** 是安全边界变更 ⇒ 落地时在 HANDOFF 明确写"新增了什么"。
3. `doc.on('change')` 的去抖策略**已定：200ms trailing**（rev45，理由见 §4 U3b）。
4. **U1/U2 都是"内核动刀"** ⇒ 每步都要跑三条基线（tsc 0 / oxlint 4 / cargo 21 passed）并截图验收。
