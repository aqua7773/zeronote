## §0 结论（先看这一段）

1. **开源移动端记账 App 里，没有「笔记应用插件」形态的先例**。最接近的两个方向是：功能完整的独立 App（Ivy / Cashew / MyExpenses / MMEX / Oinkoin）和「只做采集、不存账」的自动记账模块（AutoAccounting）。
2. **能免 Root 捕获支付通知的官方技术只有一条**：`NotificationListenerService`（用户手动授予「通知使用权」）。Xposed/LSPosed 更精准但需要 Root；无障碍读屏是补充（能读支付页面，代价大）。
3. **最值得抄的开源实现是 `WhereIsMyMoney`**（Kotlin、Apache-2.0、通知监听整套源码）：字段合并 → 关键词判定 → 金额正则 → 收支判断 → 商户提取 → 去重 → 无金额时通知栏补录。它的自动分类只是「商户 → 分类」映射，没有机器学习。
4. **与 ZeroNote 的契合度**：UI（panel / 整窗接管）、结构化存储（store）、文件（fs）、命令、事件、规则引擎 —— 都是现成的，**高**；唯一硬缺口是**原生通知监听**（需要新增一个 Tauri Android 插件，模板已有：`statusbar` / `androidperm`）。
5. **建议的 MVP**：原生插件只做「捕获 + 原文缓存 + 权限引导」；JS 记账插件做「解析 + 去重 + 分类 + 落库 + UI」；交易数据放插件 store（JSON），另导出 Markdown 月报。

## §3 技术分析：通知捕获（核心）

### §3.1 三种渠道的取舍

| 渠道 | 权限 | 覆盖面 | 稳定性 | 结论 |
|---|---|---|---|---|
| **NotificationListenerService** | 用户手动开「通知使用权」 | 微信/支付宝/银行/云闪付等所有发通知的 App | 中（文本随 App 版本变） | ✅ **MVP 唯一必做** |
| 无障碍（AccessibilityService） | 用户手动开无障碍 | 能读支付结果页、聊天页 | 低（页面结构变、耗电、审核敏感） | 二期补充 |
| 短信（SMS_RECEIVED） | `READ_SMS`（敏感权限，商店审核严） | 银行短信 | 高（文本稳定） | 可选，需单独权限 |
| Xposed/LSPosed | Root | 最全（Hook 应用内数据） | 高 | ❌ ZeroNote 不 Root |

### §3.2 机制与坑（源码核实）

`WhereIsMyMoney` 的 `PaymentNotificationListener.kt`（500 行）与 `AutoAccounting` 的 `NotificationService.kt`（156 行）做法一致：

1. **取字段**：`Notification.EXTRA_TITLE`、`EXTRA_TEXT`、`EXTRA_BIG_TEXT`、`EXTRA_SUB_TEXT`、`EXTRA_SUMMARY_TEXT`、`android.infoText`、`tickerText` —— 实际文本可能出现在任意一个字段，**必须合并**再解析（WhereIsMyMoney 用 ` | ` 拼接 7 个字段）。
2. **包名过滤**：只处理白名单包（微信 `com.tencent.mm`、支付宝 `com.eg.android.AlipayGphone`、银行 App），其余直接 return。
3. **去重**：按 `pkg + title + text` 的 MD5 去重（AutoAccounting 用 `MD5HashTable`）；WhereIsMyMoney 另生成 `transactionNo` 供文件导入去重。
4. **判定是否支付**：标题白名单（`微信支付` / `微信收款助手` / 含「支付宝」）+ 短语表（付款成功 / 收款到账 / 转账 / 红包…约 40 条）+ 含金额符号 + 支付关键词。
5. **金额正则**（按优先级）：
   - `[¥￥]\s*(\d+\.?\d*)`
   - `(\d+\.?\d*)\s*元`
   - `(?:金额|收款|付款|转账|红包|到账|成功)[：:\s]*(\d+\.?\d*)`
   - 带两位小数的数字兜底
6. **收支判断**：收入关键词（到账/收到/收款/转入/红包/退款…）优先，其次支出关键词；默认支出。
7. **商户提取**：13 条正则（`商户：` / `向(.+?)付款` / `(.+?)订单支付` …），匹配不到时用「微信支付 / 支付宝 / 快捷支付」兜底。
8. **无金额兜底**：金额为 0 也先落一条，发一条带 `RemoteInput` 的通知，让用户直接在通知栏输入金额；并附「误识别·删除」按钮。
9. **断连重连**：`onListenerDisconnected` 里 `requestRebind(...)`（AutoAccounting），避免系统回收后收不到。

**权限与限制**（官方文档 [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService)）：
- Service 必须在 `AndroidManifest.xml` 声明 `android:permission="android.permission.BIND_NOTIFICATION_LISTENER_SERVICE"` + `<intent-filter action="android.service.notification.NotificationListenerService" />`。
- 授权入口：`Settings.ACTION_NOTIFICATION_LISTENER_SETTINGS`；用 `NotificationManagerCompat.getEnabledListenerPackages(context)` 判断是否已授权。
- 系统绑定服务；App 进程被杀后，系统在下次通知时会重建 Service 进程 —— **但 Tauri 的 WebView 不会随之启动**。这条决定架构（见 §5.3）。
- MIUI/国内 ROM 还有「自启动 / 省电策略」限制，需要引导用户放开，否则服务会被杀。

### §3.3 解析的固有难点

- **双通知**：微信支付通知 + 银行扣款通知可能各来一条 → 需要按「金额相同 + 时间窗 ≤ 90s + 不同来源」合并。
- **文本漂移**：微信/支付宝小版本更新会改通知文案，规则表必须可更新（放插件里，不动 App）。
- **金额缺失**：部分通知只写「你已支付」，靠文案里的商户 + 后续补录（WhereIsMyMoney 的 RemoteInput 方案）。
- **群聊/验证码噪音**：微信消息通知极多，必须靠关键词与金额双重过滤，否则误记率高。

## §4 自动分类

### §4.1 竞品做法

| 做法 | 代表 | 效果 |
|---|---|---|
| 商户 → 分类映射（用户改一次就记住） | WhereIsMyMoney（`MerchantCategory` 表） | 简单、可解释；冷启动靠默认 |
| 关键词/正则规则 | AutoAccounting | 灵活，规则库可共享 |
| 规则引擎（条件 → 动作） | Firefly III | 表达力强，适合进阶用户 |
| AI 解析/分类 | AutoAccounting（AI 辅助）、AutoLedge | 处理长尾文本好，但需联网/模型与隐私权衡 |

### §4.2 建议的三层分类（ZeroNote 插件内纯 JS）

1. **用户映射（最高优先）**：`merchant → category`，用户改分类时写回。
2. **内置商户库**：约 100 条（美团/饿了么→餐饮；滴滴/地铁/加油→交通；京东/淘宝/拼多多→购物；星巴克/瑞幸→咖啡；话费/宽带→通讯；水电燃气→居住；医院/药房→医疗；影院/游戏→娱乐；工资/报销→收入）。
3. **关键词兜底**：文本含「外卖/餐饮」→ 餐饮；含「打车/出行」→ 交通；匹配不到 → 「其他」并标「待分类」。

可选 AI 层（默认关闭）：用户自带 API key，把「通知原文 → 分类」交给模型；隐私提示写明「会把通知文本发到你配置的模型服务」。

## §5 与 ZeroNote 的契合度

### §5.1 能力盘点（现状）

| 需要的能力 | ZeroNote 现状 | 结论 |
|---|---|---|
| 手机端 UI（列表/表单/图表） | `view.registerPanel`（sidebar/main/modal）+ 手机整窗接管（`overrideShell`，rev173.11） | ✅ 直接可用 |
| 结构化存储（交易/分类/预算） | `store`（插件自己的 JSON 持久化） | ✅ 直接可用 |
| 库内文件 / 导出 | `fs`（读写库内文件，原子写） | ✅ 直接可用 |
| 命令 / 快捷键 / 工具栏 | `command` + 手机键盘上方快捷栏 | ✅ 直接可用 |
| 事件 / 跨插件 | `event` / `service` | ✅ 直接可用 |
| 网络（AI 分类） | 插件可 `fetch`（无沙箱限制） | ✅ 可用，需隐私提示 |
| **通知捕获** | ❌ 仓库内无任何 `NotificationListenerService`（`grep notification` 为零） | **缺口** |
| 原生插件模板 | `src-tauri/plugins/tauri-plugin-statusbar`（Kotlin）、`tauri-plugin-androidperm`（权限页跳转） | ✅ 可照抄 |
| 后台常驻 | Tauri 单 Activity；插件 JS 只在 WebView 活着时运行 | ⚠️ 需缓存设计 |
| 权限引导 UI | `androidperm` 插件的「跳系统页」模式 | ✅ 可复用 |

### §5.2 缺口与代价

**唯一必须新增的原生能力**：`tauri-plugin-notification-capture`（Android 侧 Kotlin）：
- 声明 `NotificationListenerService`（manifest 合并进宿主）；
- `@Command is_enabled()` / `open_settings()` / `set_whitelist(packages)` / `drain()`（取走缓存的通知）；
- 收到通知 → 原文（pkg/title/text/time）写入**环形缓存**（SharedPreferences 或应用私有 JSON），最多保留 N 条；
- WebView 活着时可通过事件/Channel 立即推给 JS；不在时靠 `drain()` 在下次启动补处理。

**代价**：原生插件要跟着 Tauri 的插件脚手架写（Rust 壳 + Kotlin 实现 + permissions 声明），并进 `gen/android` 构建；不能只靠 `.znp` 分发 JS 插件（用户需要装新版 App）。这是本项目第一次为「后台服务」加原生能力，值得单独一个 rev。

### §5.3 推荐架构（三层）

```
[Android NotificationListenerService]        原生插件（Kotlin）
        │ 白名单包名 + 字段合并 + 原文缓存
        ▼
[tauri-plugin-notification-capture]          原生插件（Rust 壳）
        │ @Command drain() / 事件推送
        ▼
[accounting 插件（JS）]                       ZeroNote 插件
        │ 规则解析（金额/收支/商户）→ 去重 → 分类（映射+商户库）→ 落库
        ▼
[store: transactions[]]  +  [可选：导出 Markdown 月报]
        │
        ▼
[手机端 UI：列表 / 编辑 / 统计 / 预算 / 导出]
```

**为什么解析放 JS 而不是 Kotlin**：
- 规则可热更新（插件目录里改文件即生效，不用重装 APK）；
- 复用 ZeroNote 的 store/fs/UI 能力；
- 但原生侧必须缓存原文，保证「App 没开时收到的通知」不丢。

### §5.4 数据存哪

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 插件 `store`（JSON，键值） | 结构化、读写快、插件自带 | 不便直接手工编辑/搜索 | ✅ **主存** |
| 库内 Markdown（每笔一条） | 可搜索、可链接、契合笔记 | 一年数千笔会让库膨胀、列表性能差 | ❌ 不作为主存 |
| 库内 `.zn/accounting/*.json`（fs） | 可备份/可同步、与库同行 | 需自己维护索引 | 可选（想要「账本跟着库走」时） |
| Markdown **月报导出** | 人可读、可在笔记里引用 | 单向 | ✅ **导出用** |

### §5.5 契合度评分

| 维度 | 分 | 说明 |
|---|---|---|
| UI / 交互 | 9/10 | panel + 整窗接管都现成 |
| 数据存储 | 9/10 | store + fs |
| 规则/分类逻辑 | 10/10 | 纯 JS，最灵活 |
| 通知捕获 | 3/10 | 需新原生插件（模板齐全，但工作量在 Android 侧） |
| 后台可靠性 | 6/10 | 原生缓存兜底后可到 8/10 |
| 分发 | 7/10 | JS 插件可 `.znp`；原生能力随 App 版本发 |
| **综合** | **中高** | 适合作为「ZeroNote 的第一个原生能力插件」 |

### §6.4 手机端 UI（MVP）

1. **账单页**（main panel）：按日分组列表，顶部当月支出/收入/结余；点一行可改分类/金额/商户。
2. **待处理**：`confidence < 0.6` 或金额缺失的记录单独置顶。
3. **统计**：分类饼图 + 近 6 个月趋势（纯 CSS/SVG，不引图表库）。
4. **设置**：通知权限入口、白名单包名、规则编辑、导出。

## §7 风险与未决

1. **规则维护**：微信/支付宝改文案 → 规则失效。对策：规则与解析都在插件里，可发 `.znp` 更新；解析失败时保留原文进「待处理」。
2. **误识别**：通知噪音高。对策：包名白名单 + 关键词 + 金额三重过滤；每条都可在 UI 删除并「不再匹配该文案」。
3. **重复**：双通知合并（时间窗 + 金额）需要真机数据校准。
4. **保活**：MIUI 可能杀进程。对策：原生服务缓存 + 自启动引导 + 启动时 `drain()`。
5. **隐私**：通知内容可能含验证码/聊天。对策：只存白名单包名、原文仅本地、AI 分类默认关闭并明示外发内容。
6. **原生插件成本**：这是 ZeroNote 第一个后台服务型插件，需单独评估 Rust/Kotlin 构建与权限声明；若用户暂时不接受动原生层，可先做「手动记账 + CSV 导入」的纯 JS 版本。
