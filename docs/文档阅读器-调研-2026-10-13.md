# ZeroNote · 文档格式阅读器 · 调研与设计（2026-10-13）

> 状态：**active** ｜最后核对：2026-10-17 ｜权威范围：文档阅读器选型与实测

## §0 范围（用户明确）

| 做 | 不做 |
|---|---|
| PDF（pdf.js 自绘 canvas 阅读器） | ❌ 编辑 / 批注 / 高亮 |
| EPUB / MOBI / AZW3 / FB2 / CBZ（foliate-js） | ❌ 最近打开列表 · 书签 · 阅读进度记忆 |
| TXT（纯文本直显） | ❌ 缩略图 · 双页 · 语音朗读 |
| 文件树里**看得见**这些文档、点一下即开（rev73 起统一收进虚拟「文档 N」分组，见 §6） | ❌ DOCX / RTF / CBR（见 §1.3 的体积与收益判断） |

## §1 选型

### §1.1 结论

| 用途 | 选谁 | 版本 | 许可证 | 离线体积（实测） |
|---|---|---|---|---|
| PDF | **pdf.js**（`pdfjs-dist`） | **6.4.299** | Apache-2.0 | 5.00 MB（`pdf.min.mjs` 458.9 KB + `pdf.worker.min.mjs` 1.23 MB + `cmaps/` 1.11 MB + `standard_fonts/` 780 KB + `wasm/` 1.47 MB） |
| 电子书 | **foliate-js** | **1.0.1** | MIT | 290 KB（14 个 js + `vendor/zip.js` + `vendor/fflate.js`） |

合计 **5.28 MB**，放**应用内置资源** `public/vendor/`（随 vite 打进 `dist` ⇒ 生产是 `<origin>/vendor/…`）。

### §1.2 为什么是这两个（生态惯例，一手来源）

- **pdf.js 是业界唯一选择**：Obsidian 内建 PDF 阅读器（v1.3 起）基于它、Logseq 用 `pdfjs-dist`、Zotero 有专门的 `PDFJS_CONFIG=all|zotero|mobile` 三套构建、Readest 直接用它的 legacy worker。
- **EPUB 正在从 epub.js 迁往 foliate-js**：`epubjs@0.3.93` **停更于 2022-02-17**、8 个运行时依赖、强耦合同源 iframe；Obsidian 的 `ob-epub-reader` 至今还要 `patch-package` 给它打补丁。2025 年后的新实现（Readest、`obsidian-epub-viewer`）清一色 **foliate-js**（MIT，1133★）。
- **必须自绘，不能指望 WebView 内建**：HTML 规范对所有 sandboxed frame 强制 *sandboxed plugins* browsing context flag（无 token 可取消），且本仓 CSP 有 `object-src 'none'`；WebView2 的内建 PDF 查看器内联 embed 请求至今 open 且被标 `priority-low`。⇒ **两端都必须自带渲染器**。
- **排除项**：`@react-pdf-viewer/core` **不是开源**（LICENSE 全文 88 字节：「You have to purchase a Commercial License」）；`TeamMaestro/pdf-viewer` 表面是 Web Component，实际 27 处 iframe 操作官方 `viewer.html`（`contentDocument` 同源操控）⇒ 在 ZeroNote 的 opaque origin 里直接失效。

### §1.3 没做的格式（判断依据）

| 格式 | 为什么不做 |
|---|---|
| RTF | 唯一可用库 `rtf.js` 自身 **10.9 MB**（比整个 pdf.js 还大），收益不抵体积 |
| CBR（RAR 漫画） | 需 `libarchive.js` 2.21 MB（WASM + Worker 双重 CSP 风险）；Readest 明确标注不支持 |
| DOCX | `mammoth` 1.59 MB / `docx-preview` 955 KB 可行，但排版保真有限 —— 属"想要再加"的第二批 |

## §2 实测证据（全部本机跑出来的，不是推断）

### §2.1 asset 协议：两端都能读库内文档

用一次性夹具 `examples/asset-probe/`（结果写进插件 store + 库根 JSON，便于 adb 直读）：

| 环境 | 目标 | 实测 |
|---|---|---|
| 桌面（CDP `fetch`） | `_tmp-vault-tb/probe.pdf` | `200` · `application/pdf` · 449 B · `Range: bytes=0-9` → **`206` + `content-range: bytes 0-9/449`** |
| Android 真机（插件内 fetch） | `.zn/plugins/asset-probe/probe.pdf` | **`403`**（空体） |
| Android 真机 | `probe.pdf`（**库根**） | `200` · `application/pdf` · 449 B · Range → **`206`** |

**根因（一手源码）**：`tauri-2.12.3/src/scope/fs.rs:215-225` ——
`require_literal_leading_dot` 在 **unix 默认 `true`、windows 默认 `false``**，
于是 Android 上 glob `**` **不匹配"点开头的路径段"**，而 `.zn` 恰好是点开头 ⇒ `scope.is_allowed()` 返回 false ⇒
`asset.rs:52-54` 直接 403。

**修法（已落地）**：`src-tauri/tauri.conf.json` 的 `assetProtocol.scope` 从数组改为对象形式，
显式写 `"requireLiteralLeadingDot": false`（该字段在 `@tauri-apps/cli/config.schema.json:1399` 有定义）。
✅ **2026-10-13 真机复验通过**：重新构建并安装 Android 二进制后，同一个 `.zn/plugins/asset-probe/probe.pdf`
（**点开头目录**）从 **`403` 变成 `200`**（`application/pdf`、Range `206`）⇒ 这条修复确实生效。
（`assetProtocol` 是**编译期嵌入**的，改完必须重出 Android 二进制；桌面不受影响，Windows 本来就是 `false`。）

> 附带记录一条**旧结论作废**：tauri issue #11371（「fetch/XHR 响应没有 `content-range` 头」，
> 原文点名影响 pdf.js 分段加载）报于 2024-10，**在本仓当前的 tauri 2.12.3 上已不复现** ——
> 实测 Range 返回 `206` 且头齐全。Readest 为此自建了 `rangefile.localhost` 协议，我们不需要。

### §2.2 worker 与 CSP：不用改 CSP（一次推断被实测+规范纠正）

- 实测：`new Worker(URL.createObjectURL(new Blob(['self.postMessage(1)'])))` → **`ok`**（未被拦）。
- 机制（一手来源，MDN `worker-src`）：`worker-src` 缺失时的回退链是 **`child-src` → `script-src` → `default-src`**，
  而本仓 `script-src` 含 `blob:` ⇒ blob worker 放行。
- ⚠️ 我最初的推断是「worker-src 只回退到 default-src ⇒ blob worker 会被拦」，**错了**。CSP 一个字都不用改。

### §2.3 pdf.js 端到端渲染（CDP 实测）

```
ok: true · pages: 1 · viewport: 300x200 · nonWhite: 1737
```
（`nonWhite` 是 canvas 上的非白像素数 = 那行 `ZeroNote PDF probe` 文字；且 `getImageData` 未抛跨域异常
⇒ asset 协议的 canvas **没有被污染**，将来要"导出当前页为图片"也是可行的。）

### §2.4 真 DOM 里的 sandboxed iframe（foliate-js 的前提）

foliate-js 自己建 iframe 并自己设 sandbox（`paginator.js:234`）⇒ 只要宿主给真 DOM 就能工作。
实测（宿主 DOM 内建 `sandbox="allow-same-origin allow-scripts"` 的 blob iframe）：

| 判据 | 结果 |
|---|---|
| 父可访问 `contentDocument` | ✅ `ok` |
| iframe 内 CSS 生效 | ✅ `getComputedStyle` 得 `rgb(1,2,3)` |
| iframe 内**内联脚本** | ⚠️ **`scriptRan: true` —— 执行了** |

第三行是**必须记住的坑**：rev30 的结论「`data:`/`blob:` iframe 里的内联脚本会被 Tauri 注入的 `sha256` 拦掉」
**只在生产构建成立**（`'unsafe-inline'` 被 hash 抵消）；**dev 下 CSP 就是 `tauri.conf.json` 里那份，含 `'unsafe-inline'` ⇒ 脚本会跑**。
⇒ **不能把"脚本不执行"寄托在 CSP 上**（dev 与生产行为不一致 = 最危险的那类差异）。

**因此我们改动了第三方源码**（见 §4.2）：把 foliate 那两处 iframe 的 `allow-scripts` **去掉**，
不再给章节脚本任何执行机会（`allow-same-origin` 保留 ⇒ 分页/测量仍能读 `contentDocument`）。
两端都是 Blink（WebView2 / Android System WebView），不需要 foliate 注释里那个 WebKit bug 218086 的绕法。

### §2.5 真机专属的两个坑（**桌面测不出来**，都踩过了）

#### (1) pdf.js 的 modern build 在 Android WebView 上必炸 —— 而且 legacy 也不够

真机（Android 16 · System WebView **Chrome 143**）打开 PDF 报
`TypeError: this[#da].getOrInsertComputed is not a function`；**桌面 WebView2（Chrome 154）同代码正常**。
`Map.prototype.getOrInsertComputed` 是很新的 TC39 提案。

**两步才修好（都有实测）**：

1. 换 **legacy build**（`legacy/build/pdf.min.mjs` 523.8 KB vs modern 458.9 KB，**只大 12%**）。
   ⚠️ **但 legacy 只做语法转译、不带这个 API 的 polyfill** —— 实测换 legacy 后 `getDocument` 能解析出
   `pages: 1`，**仍然倒在渲染那一步**（同一个 `getOrInsertComputed` 报错）。
2. 插件里补 **3 行 polyfill**（`ensureMapApis()`：`Map.prototype.getOrInsertComputed` 存在则跳过）⇒ 通过。
   真机复测 `300x200` / `nonWhite 1610`；桌面复测 `nonWhite 1737`
   （数值差异来自抗锯齿/字体，属正常）。

> 同构先例佐证：Readest（Tauri 2 + Android）用的也是 **legacy worker**，并且它的 `tauri.conf.json` 里
> 显式写了 `webview-upgrade.minSupportedMajor: 111`。

#### (2) vite dev server **启动时就把 `public/` 的文件列表定死**

把 pdf.js 从 `public/vendor/pdfjs/build/` 换到新目录 `public/vendor/pdfjs/legacy/` 之后，真机上：

| URL | 实测 |
|---|---|
| `/vendor/pdfjs/legacy/pdf.min.mjs`（**启动后新增**） | `200` 但 `content-type: text/html`、**981 字节**（SPA 的 `index.html`） |
| `/vendor/foliate/view.js`（启动时就存在） | `200` · `text/javascript` · 22314 字节 ✅ |

**诊断法（省时间）**：同时 fetch 两个 URL、**对账 `content-type` 与长度** —— 一眼分清"路径没被收录"与"MIME 问题"。
探针里已内置这段（结果里的 `urls` 字段）。

**规避**：dev 下**新增** public 文件，要么**重启 vite**，要么**放回既有目录名**
（本插件选后者：`build/` 目录里放的就是 legacy 那份，代码注释写明原因）。
**生产构建没有这个问题** —— `pnpm build` 全量复制 `public/`（实测 `dist/vendor` 217 文件 / 5.53 MB）。

> 顺带一条环境事实：**Android 上页面的 `location.origin` 是 `http://tauri.localhost`**（不是 vite 的地址），
> 所以插件里用 `location.origin` 拼绝对 URL 是正确做法。探针把 `origin` 也记了下来，便于日后对账。
>
> 再一条：真机模拟点击 —— `input tap` 在 WebView 里无效、原地 `swipe x y x y 120` 这次也无效，
> **`input motionevent DOWN x y` + `UP x y`（隔 ~120 ms）有效**；`screencap` 是物理像素，可直接当坐标用。

## §3 架构落点

```
文件树（内核）── kind='doc' 的条目 ──▶ core.openDocument（内核注册的**派发点**）
                                            │  默认实现：toast「没有能打开 .pdf 的插件」
                                            ▼  插件 command.bind 接管（卸载自动还原）
                                   examples/doc-reader
                                            │
                       ┌────────────────────┴────────────────────┐
                       ▼                                         ▼
        host.assetUrl(库内路径) + fetch                 view.overrideShell（真 DOM）
                  → Blob                                  → 自绘顶栏 + body
                       │                                         │
        ┌──────────────┴──────────────┐              ┌───────────┴───────────┐
        ▼                             ▼              ▼                       ▼
  pdf.js（canvas 自绘）        foliate-js（<foliate-view>）
```

**四个设计选择与理由**

1. **内核只做"派发"，不认识具体格式**：内核新增 `NoteMeta.kind`（`note` / `doc`）与命令 `core.openDocument`，
   默认实现只是如实提示"没有插件能开"。插件用 **`command.bind`** 接管 —— 复用 rev49 已有的机制
   （只换实现不动元数据、卸载自动还原、审计能看到 `impl: plugin:doc-reader`）。
2. **载体是 `view.overrideShell`（真 DOM）**，不是 `registerWebView` 的 iframe：后者是 opaque origin，
   既跑不了 pdf.js 的 canvas，也读不到 foliate 需要的 `contentDocument`。
   接管由**用户动作**（点文件树里的文档）触发，符合契约 §2.8 的插件义务（不要 onStartup 自动接管）。
3. **渲染资产放应用内置**（`public/vendor/`）：插件入口跑在 Blob 模块里，**相对导入没有 base 目录**
   （契约 §3.2）⇒ 若把库塞进插件目录，就得自己打包成单文件、且 cmaps/字体这类**二进制**还得另外想办法读出来。
   放应用内置后，插件用**绝对 URL** `import(new URL('/vendor/…', location.origin))` 即可，
   相对导入正常解析、二进制资源走同源 http、CSP 一个都不用加。
4. **字节用 asset 协议取，不用 `fs.readText`**：后者按 UTF-8 读，二进制必坏；内核也**没有**任何二进制读命令。

## §4 对第三方源码的改动（全部留痕）

`public/vendor/` 下的代码是**逐文件复制的上游产物**，只动了两处，都在原处写了 `⚠️ ZeroNote 改动` 注释：

| # | 文件 | 改动 | 理由 |
|---|---|---|---|
| 1 | `foliate/fixed-layout.js:1` | 删掉 `import 'construct-style-sheets-polyfill'` | **裸模块名在浏览器里无法解析**；两端都原生支持 `adoptedStyleSheets`，不需要这个 polyfill |

## §5 未验 / 未做（诚实清单）

1. **Android 真机复验 `requireLiteralLeadingDot: false`** —— 需要重新构建 Android 二进制（编译期嵌入），本轮看 rev72 结果。
2. **`platforms` 声明**：插件写了 `["desktop","android"]`，两端都有渲染器；但 Android 上的**性能**（大 PDF 渲染、EPUB 分页）
   未压测，官方 FAQ 提到一页 Letter 大小的 HiDPI canvas 可能占 ~14 MB。
3. **EPUB 章节的相对资源**（图片/CSS）由 foliate 的 loader 处理 ✓（本轮测试书只用了一份外部 CSS，图片未测）。
4. **超大文件**：pdf.js 走 asset 的流式 + Range，理论上不整份进内存；但插件没有做大小上限提示。
5. **`content://`（Android SAF）** —— 仍然读不了（历史结论不变，与本插件无关）。
6. **不做**：最近文件 / 书签 / 进度 / 缩略图 / 目录侧栏（EPUB 的目录数据 `book.toc` 已经拿得到，是"想要再加"）。

## §6 文件树怎么摆这些文档（rev73，用户要求）

用户原话：「侧栏文件列表里面，把 pdf、epub 等其他格式文件都收纳在一个目录下」。

**这是 UI 层聚合，不是移动文件**：`FileTree.tsx` 的 `buildTree` 把 `kind === 'doc'` 的条目从各自目录里抽出来，
挂到一个**虚拟分组节点**「文档 N」（`virtual: true`，哨兵路径 `__zn_docs__`，**固定排在树末尾**）。

| 项 | 行为 |
|---|---|
| 折叠 / 展开 | 支持（与其它目录节点一致） |
| 右键 | **不弹菜单** —— 它不对应磁盘目录，任何文件操作都会打到假路径 |
| 组内的文档 | 照旧：点击 → `core.openDocument` → 阅读器；右键仍有正常的重命名 / 删除 / 复制 |
| 文件本身 | **一动不动**（路径不变、仍在原目录）；真实位置由每行的 `title`（悬停）交代 |

顺带修一个既有 bug：**重命名只在"没有扩展名"时才补 `.md`** —— 否则把 PDF 改名会变成 `手册.pdf.md`
（此前树里只有 `.md`，这条分支命不中非 md；文档进树后才暴露）。

## §7 删除：逻辑删除 ＋ 物理删除（rev74，用户要求）

用户原话：「阅读插件应该提供右键两个删除功能，逻辑删除和物理删除」＋「允许多选」。

| 位置 | 入口 | 多选 |
|---|---|---|
| **阅读器内**（插件自绘） | 顶栏**「删除」**＋**右键** | ❌ 接管期间没有列表可多选 |
| **文件树**（内核） | 右键「彻底删除…」 | ✅ 多选时「彻底删除选中的 N 项…」 |
| 手机多选条 | 「彻底删除」（触屏唯一批量入口） | ✅ |

**语义差别（都由内核既有边界决定）**：

- **逻辑删除** = `fs.delete(path)` → 移入 `.zn/trash/`，**回收站里能恢复**。
- **物理删除** = **两步**：`fs.delete` → `listTrash` 按 `originalPath` 找回 id → `fs.purgeTrash(id)`。
  ⚠️ **内核没有"直接抹掉库内文件"的命令**；而 `delete` 的返回值（`.zn/trash/<stamp>/<名>`，**带斜杠**）
  **不能**当 `purgeTrash` 的 id —— 后者明确拒绝带斜杠的 id（`src-tauri/src/lib.rs:561`）。
  ⚠️ 也**不能**用 `emptyTrash`（会把用户之前删的一并清掉，只该删本次选中的）。
  中途失败就停在"已在回收站" ⇒ **不会丢数据**。
- 物理删除一律**二次确认**（自绘浮层）；逻辑删除沿用既有的「撤销条」。
