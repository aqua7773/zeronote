## §4 下一步（原生层，约 2–3 小时）

可行方向，按代价从低到高：

1. **`WebView.onRenderProcessGone`**（Kotlin）：只在渲染进程**死掉**时回调 —— 我们的现场是「进程活着但不出帧」，**大概率收不到**，先验证成本低。
2. **绘制回调计时**：在 Android 侧包一层 `ViewTreeObserver.OnPreDrawListener` 或自定义 `WebView` 子类统计 `onDraw` 次数；N 秒（如 30 s）没有一次绘制 ⇒ `webView.reload()`。
   - 风险：WebView 内部有脏区域优化，正常空闲时也可能不重绘 ⇒ 阈值要宽（60 s+），并排除「页面不可见」。
3. **Surface 生命周期**：`SurfaceHolder.Callback` / `onSurfaceDestroyed` —— 若白屏伴随 Surface 被销毁，这条最准。
4. **读渲染进程 CPU/状态**：`/proc/<renderer_pid>/stat` 的 utime+stime 长时间不变 ⇒ 判定停摆（但读别的 uid 的 proc 需要权限）。

**接入位置**：`src-tauri/gen/android/app/src/main/java/com/aqua/zeronote/MainActivity.kt`（目前很薄，只做 edge-to-edge），或新加一个 `TauriPlugin`（参考 `src-tauri/plugins/tauri-plugin-statusbar/` 的 Kotlin 侧写法）。

**注意**：改 Android 后必须**重新构建 dev 包**（`pnpm tauri android dev`，约 8–10 分钟），只改前端热更新不生效。

## §4.5 原生层实现（rev173.347 · 2026-11-04）

**做法**：不用「JS 心跳」，也不用「View 层的绘制回调」，而是**把 WebView 自己画到一张图上，看画出来是什么**。

`src-tauri/gen/android/app/src/main/java/com/aqua/zeronote/RenderWatchdog.kt`（新文件）：
`MainActivity.onWebViewCreate()` 拿到 WebView 引用 → `onResume` 启动，每 10 秒一次：

1. `webView.draw(canvas)` 画到 **1/4 缩放**的 Bitmap（1220×2712 → 305×678），走 Chromium 的软件绘制路径；
   渲染进程停摆时画出来是白/空，正常时是页面内容。
2. 在图上取 **5 条全宽横带**（窗口高度 10% / 30% / 50% / 70% / 90%，各 8px 原像素）。
3. 五条都 ≥97% 近白（单通道 ≥240）⇒ 本次采样「画面全白」。
4. 全白时用 `evaluateJavascript` 问一句 DOM 是否正常（`.zn-app` 在且有子元素）。
   **DOM 正常 + 画面全白** = 渲染停摆；DOM 挂了 = 普通空白页/加载失败，归 JS 层处理，这里不动手。
5. 连续 **6 次**（60 秒）成立 ⇒ `webView.reload()` **一次**（进程内 `rescued` 标记，不循环救）。

**第一版用 `PixelCopy` 为什么失败**（真机实测 · 2026-11-04 00:48）：
`PixelCopy.request(window, rect, …)` 只抓窗口主 Surface，而 Tauri 的 WebView 内容在**独立 `SurfaceControl` 子层**
（`dumpsys SurfaceFlinger --list` 能看到 `MainActivity#40938` 下面还有 `#40939`；
`uiautomator dump` 显示 WebView 是叶子节点、没有 SurfaceView）。结果：页面明明有内容（截图 88 KB），
抓回来五条横带全是 1.00 纯白 —— **读数与真实画面不一致，方案作废**。

**第二版用 `webView.draw(canvas)` 为什么也不行**（真机实测 · 2026-11-04 00:53 / 00:57）：
硬件加速下 Chromium 不往软件 Canvas 里画页面内容 —— 页面有内容（截图 88 KB）时 draw 出来仍是全白。
**自检也没拦住**：自检用的「铺整屏红色 div 再 draw」能画出红色（简单合成层能画），
于是误判成「draw 可用」→ 正常页面被连续判白 → 触发了 1 次误 reload（00:56:44）。
⇒ **结论：Tauri Android WebView 上，应用层拿不到「用户看到的画面」**，两条路都堵死。

**当前保留的探针**（`ZN-RENDER` 日志）：判据仍是「五条横带全白 + DOM 正常」，
但阈值拉到 **30 次（5 分钟）**，动作从 `reload()` 换成**软复位**（`webView.onPause()` → 800ms →
`onResume()`）—— 依据是用户真机实测「白屏后切后台 10 秒再回来会恢复」，说明这条停摆可以被
WebView 的 pause/resume 生命周期打断；reload 实测无效（00:56:44 reload 后仍全白）且会丢未保存内容。
**这一版仍是「无害的尝试」**：正常页面上最多每 5 分钟一次极短停顿，不会刷新页面、不会丢内容。

**为什么不用文档 §4 里的另外三条**：

| 方案 | 为什么不用 |
|---|---|
| `WebViewClient.onRenderProcessGone` | 只在渲染进程**死掉**时回调；现场是进程活着但不出帧 ⇒ 收不到 |
| `OnPreDrawListener` / 自定义 View 的 `onDraw` | 硬件加速下内容由合成器直出，`onDraw` 只反映主线程 draw pass，白屏时主线程一直很忙 ⇒ 测不出 |
| `/proc/<renderer_pid>/stat` | Android 10+ 读不到别的应用 uid 的进程状态 |

**日志**：tag `ZN-RENDER`，每 10 秒一行采样读数（`bands=[…] allWhite=… streak=…`），
`adb logcat -s ZN-RENDER` 就是验收时唯一的现场证据来源。

## §8 rev173.349 实测（2026-11-04 01:57）—— 软复位能跑，但判据是误判

**现场**（`33b676f6` · debug 包 · dev server）：

| 时刻 | 事实 |
|---|---|
| 01:52 | `location.reload()` 后页面**完全正常**：三张笔记卡片，截图 88,515 B |
| 01:52–01:57 | `ZN-RENDER` 每 10 秒一行：`bands=[1.00,1.00,1.00,1.00,1.00] allWhite=true` + `domProbe=true domAlive=true` |
| 01:57:43 | `streak=30/30` ⇒ **软复位执行**（01:57:44 `软复位完成`，streak 归零） |
| 复位前后 | 截图逐字节同尺寸（88,515 B），画面**没有任何变化** ⇒ 从头到尾就没白过 |

**结论三条**：

1. **软复位动作本身可用** —— 日志、时序、"只做一次"的 `rescued` 标记都按设计工作，无崩溃。
2. **`webView.draw()` 在本机永远画不出页面内容**：页面正常时五条横带同样是 1.00 全白。
   `verifyDraw` 用「铺整屏红色 div 再 draw」做自检**区分不了**这种情况 —— 红色能画出来（说明简单合成层能画），
   但 Chromium 的文本 / 卡片 / 图片画不出来。⇒ 自检通过 ≠ 读数可信。
3. **当前实现的净效果**：每个进程在没有白屏的情况下白做一次 800 ms 的 `onPause→onResume`
   （肉眼可能看到一次极短停顿）。这是**误判**，不是保护。

**下一步（待拍板，不自行改）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 停用自动判据 | `RenderWatchdog` 只记日志不再 `rescue()`（或整个 start 不调） | 5 分钟；白屏时不再有任何自愈 |
| B. 改手动触发 | 保留软复位，但由用户主动触发（设置页按钮 / 音量键组合 / 长按某处） | 半天；白屏时用户得知道怎么按 |
| C. 继续找判据 | 需要一条「渲染进程真出帧」的可读信号；§3/§4 已证伪 JS 层与 App 层两条路 | 未知，可能无解 |

> 用户实测「切后台 10 秒再回来能恢复」仍然是**唯一被证实有效**的恢复手段；
> 软复位就是把这件事自动化，缺的只是一个不误判的触发条件。

## §9 类型 A：页面没挂载（rev173.349 已兜底）

**现象**（2026-11-04 01:24 现场，与上面的渲染停摆**不是同一类**）：

- 页面纯白（19,399 B），但 DOM 是空的：`#root` 无子节点、`document.head` 里连 `styles.css` 的
  `<style>` 都没有、root 上没有 React 容器标记 ⇒ **`createRoot` 根本没执行**
- `performance` 资源记录：`@vite/client` 返回 **500**、`main.tsx` 耗时 **13.7 秒**
- `location.reload()` 一次即恢复

**兜底**（`index.html` 内联脚本，rev173.349 · 不依赖任何模块 —— React 里那三套此时都不存在）：

1. 判据：`window.__znBooted`（`main.tsx` 在 `createRoot().render()` 之后置位）或 `#root` 已有子节点
2. 25 秒内两者都没有 ⇒ **自动重载一次**（`sessionStorage` 的 `zn.boot-rescue-done` 防死循环）
3. 重试后仍失败 ⇒ 显示错误卡片（「页面没能加载起来」+ 原因 + 重载按钮），不再无限刷新
4. `<script>` / `<link>` 的 error 事件**立即**触发，不用等 25 秒
5. 正常启动完成后停掉自检并清掉重试标记

**验证**（真机 `33b676f6` · CDP `Network.setBlockedURLs` 拦截 `main.tsx`）：

| 步骤 | 结果 | 证据 |
|---|---|---|
| 拦截 + reload | 自动重载一次，第二次显示错误卡片 | `_shots/zn-typea-2.png` · `sessionStorage["zn.boot-rescue-done"]="1"` |
| 解除拦截 + reload | 页面恢复、卡片消失、标记清空（`__znBooted=true`、`flag=null`） | `_shots/zn-typea-3-restored.png` |
| 单测 | `tests/boot-guard.test.ts` 7/7 | — |

**边界**：只覆盖「HTML 加载了但模块没执行」。**整个导航失败**（dev server 挂掉、连不上 `tauri.localhost`）
时页面是 Chromium 自己的错误页，内联脚本根本不执行 —— 那条要靠原生 `WebViewClient.onReceivedError`（未做）。
