## §0 用户原话与范围

> 「**沙箱不做**，只进行**卡死直接触发闪退**，**自动关闭卡死插件**，**重进就解决了**。」

| 做什么 | 不做什么 |
|---|---|
| ① 主线程卡死 → **应用直接闪退**（不让用户干等） | ❌ 沙箱 / Worker 隔离 / 内存与时长上限（用户已裁决搁置） |
| ② 下次启动**自动禁用**那个卡死的插件 | ❌ 进程隔离、权限门（原则 4 已明确内核不设防） |
| ③ 重进即可用（一键可恢复被禁用的插件） | ❌ 覆盖"单个面板崩"（`PanelBoundary` 已管）/ 覆盖内核代码被改坏（`修复内核.cmd` 已管） |

## §1 为什么"闪退"必须由**原生侧**触发（一手依据）

**插件是进程内 JS，`while(true)` 卡住的是 WebView 的 JS 主线程。**

- JS 单线程 ⇒ 主线程被占死时，**前端自己的 `setInterval`／心跳／看门狗一律不执行**，
  所以"前端检测自己卡死"在逻辑上不可能。
- 结论：**判超时的一方必须在另一个线程上** —— 这里是 Rust（Tauri 的原生侧），
  它有自己的 OS 线程，不受 WebView 主线程影响。

> 已有一处同源认知（契约 §4）：`while(true)` 目前能卡死整个应用，这正是当初"沙箱"想解决的问题；
> 用户改为"不做沙箱，只做崩溃后能回来"的路子 —— 本条即其落地。

## §2 方案（三段，都可独立开关）

### §2.1 A 段：心跳 + 原生看门狗

| 部分 | 做法 |
|---|---|
| 前端心跳 | 页面可见时 `setInterval(() => invoke('zn_heartbeat'), 1000)`；**不可见时不发** |
| Rust 记录 | 全局 `AtomicU64` 存"最后一次心跳的毫秒时刻" |
| Rust 检查 | 一个 `std::thread` 每 1 s 醒来一次：`now - last > TIMEOUT` **且未处于暂停态** ⇒ 判定卡死 |
| 超时阈值 | 默认 **5000 ms**（≈ 连丢 5 次心跳），可用 `ZN_WATCHDOG_TIMEOUT_MS` 覆盖 |

**阈值依据（诚实标注）**：正常长任务（大文件渲染、全文索引、大库列表）实测在数百毫秒量级；
5 s 给足了 GC / 大渲染的余量，又能把"卡死"从"卡一下"里分出来。**具体数字建议实施时用一次
真实大库压测校准**，不要照抄。

### §2.2 B 段：闪退

- 判定卡死 ⇒ **`std::process::exit(101)`**。
  - 为什么不用 `app.exit(0)`：Tauri 的退出走 `RunEvent::ExitRequested` → 可能需要主线程参与清理；
    **主线程已死**，很可能又卡住。`std::process::exit` 是进程级立即终止（标准库语义：
    不跑析构、不做清理），只依赖当前这个 Rust 线程 ⇒ 卡死时唯一可靠的一条路。
  - 退出码 **101**（= Rust panic 惯例码）便于事后从日志分辨"这是看门狗杀的"。
- ⚠️ **未实测项**：从**非主线程**调用 `std::process::exit` 在 Tauri/Android 上是否真能终止进程 ——
  见 §6 前置探针（这是本方案的第一个要验的假设）。

### §2.3 C 段：启动自愈（自动关闭卡死插件）

**机制（三段标记）**

1. 前端在 `loadPlugin(id)` **之前**：`localStorage['zn.plugin.loading'] = JSON.stringify({ id, t: Date.now() })`
   —— `localStorage` 是**同步**写，卡死在 `apply()` 里也已经落盘。
2. 加载**走完**（成功或可捕获的失败）⇒ `delete localStorage['zn.plugin.loading']`。
3. **应用启动时、扫插件之前**读该键：非空 ⇒ 上次**没能走完这次加载** ⇒ 把 `id` 加入禁用集合。

**为什么"禁用"是合理的默认处置**：标记非空只有两种原因 —— (a) 插件真的卡死了（要抓的就是它）；
(b) 用户在加载途中强杀/系统回收进程。**两者无法区分**，一律按 (a) 处理；但——

**三条防"静默失效"的硬要求（原则：静默失效比报错危险）**

1. **必须可见**：插件管理页对这类插件显示标记「**因上次加载未完成已自动禁用**」，
   与用户手动禁用的显示区分开（一个是"你关的"，一个是"我替你关的"）。
2. **必须可一键恢复**：「重新启用」按钮（复用已有 `togglePlugin`）。
3. **必须留痕**：写一条日志（`host.log`）+ 一条 toast：「上次加载「X」时卡死，已自动禁用它（可在插件管理里重新启用）」。

**正常路径必须清标记**（否则会误禁用）：除加载完成外，**应用正常退出/关窗**时也要清
（主窗口已有"关窗前落盘"监听器，挂在那里即可）—— 这样"用户正常关应用"不会留下残留。

> 同型先例（可借鉴其"有界恢复"思路）：Tolaria 的前端就绪看门狗 ADR
> （[ADR-0104](https://github.com/DavidAlphaFox/tolaria/blob/main/docs/adr/0104-tauri-frontend-readiness-watchdog.md)）
> 用 `sessionStorage` 记"这次启动已经补救过一次"，**明确拒绝无限循环补救**。
> 我们的标记同理：只处理"上一次留下的痕迹"，不做循环。

## §3 防误判（本方案最容易出事的地方）

**误判来源与对策（逐条）**

| # | 误判来源 | 对策 |
|---|---|---|
| 1 | **手机切后台** —— WebView 被系统暂停，心跳自然停 ⇒ 会被当卡死杀掉 | 监听前后台并**暂停计时**（见下）；恢复前台时把 `last` 重置为当前时刻（否则一恢复就立刻超时） |
| 2 | **桌面窗口最小化 / 失焦** | 前端按 `document.visibilityState` 主动暂停/恢复（双保险；WebView2 最小化时 JS 定时器一般不冻结，但不赌） |
| 3 | **页面正在 reload / HMR** （dev 与验收脚本会频繁发生） | **dev 默认关**（§4），生产才开 |
| 4 | 长任务（大库索引、大文件渲染） | 阈值 5 s + 实施前压测校准 |

**前后台事件用哪个 API（一手核实，别记错）**

读了本地 `tauri-2.12.3/src/app.rs`：

- `WindowEvent::Suspended` / `Resumed` —— **`#[cfg(mobile)]`**，注释原话：
  *"**Android**: This is triggered by `onPause` method of the Activity"* / `onResume`；**桌面不支持**。
- ⚠️ **`RunEvent::Resumed` 不是移动端生命周期事件**！它写的是
  *"Sent if the event loop is being resumed"*（事件循环层面）。**别拿它判"回到前台"**。
- ⇒ 移动端接 `RunEvent::WindowEvent { event: WindowEvent::Suspended }`；
  桌面用前端的 `visibilitychange` 通知（`zn_watchdog_pause` / `zn_watchdog_resume`）。

## §4 dev 下怎么关（避免开发期被自己杀）

- Rust 侧读环境变量：`ZN_WATCHDOG=off` ⇒ 完全不启动看门狗线程（连日志都不打）。
- **`dev.cmd` 与 `android-dev.cmd` 里默认设 `ZN_WATCHDOG=off`**；生产包不带这个变量 ⇒ 默认开。
- 理由：dev 下页面 reload / HMR / 验收脚本会让心跳断几秒，误杀只会浪费轮次。
- 另留 `ZN_WATCHDOG_TIMEOUT_MS`（调阈值）与 `ZN_WATCHDOG_DRYRUN=1`（**只记日志不退出**）——
  dryrun 用于"先观察一段时间，看它会不会误判"。

## §8 代价与诚实边界（写清，别让人以为这是防护）

1. **卡死期间未保存的手改会丢** —— 主线程已死，无法落盘。自动保存 800 ms ⇒ 损失窗口通常 ≤ 1 秒，但**这是真的会丢**。
2. **"自动禁用"可能误伤** —— 用户在加载途中强杀应用会留下标记 ⇒ 下次误禁用那个插件。代价可接受（**一键恢复 + 明确标记**），但必须承认它存在。
3. **不是沙箱** —— 恶意插件照样能删库、能写库外（原则 4 原话："内核不提供任何安全保证"）。本机制只解决"应用被卡死之后怎么回来"。
4. **不覆盖**：单面板崩溃（已有 `PanelBoundary`）· 内核代码被改坏（已有 `修复内核.cmd`）· 数据损坏（无版本化，属另一个决定）。
5. **未实测三项**见 §6；**阈值数字**待压测校准。

## §11 白屏兜底的真实边界（2026-10-29 · rev173.246 实测核实）

> `docs/ROADMAP.md` §3.4 长期挂着「白屏兜底边界」这条小债，原话是
> 「实测 `Page.crash` 与 `window.close()` 会让窗口壳一起消失 ⇒ 兜底实际覆盖的是『页面没起来 / JS 停了』」。
> 本轮把它逐条核实 —— **那句话只对 `window.close()` 成立，`Page.crash` 是反的。**

机制在 `src/lib/window-guard.ts`（rev173.104）：子窗口每 3 s 向主窗口报一次活（附带自检 `domLooksAlive`），
主窗口每 5 s 扫窗口列表，把「没心跳 / 心跳断了 / 连续 3 次自报白屏」的 `plugin-*` / `note-*` 窗口 `destroy()`。

| 情形 | 窗口壳还在吗 | 兜底生效 | 依据 |
|---|---|---|---|
| 子窗口**渲染进程崩溃**（CDP `Page.crash`） | **还在** | ✅ 心跳停 12 s ⇒ destroy | 本轮实测（见下表的对照实验） |
| 子窗口 **JS 全挂**（死循环 / 页面被换掉） | 还在 | ✅ 同上 | `tests/window-guard.test.ts` 的 `pickStuckWindows` |
| 子窗口 React 树被清空 / 根节点零尺寸 | 还在 | ✅ 连续 3 次 `domLooksAlive=false` ⇒ destroy | 同上 |
| 子窗口里 `window.close()` | **没了** | 不需要 | 一手源码 `wry-0.55.1/src/webview2/mod.rs:615` —— `add_WindowCloseRequested` 的处理器直接 `DestroyWindow(hwnd)` |
| label 不以 `plugin-` / `note-` 开头的窗口 | 还在 | ❌ 不参与守护 | 本轮实测（`crash-test` 40 s+ 仍在） |
| **主窗口**自己「DOM 空但 JS 活」的白屏 | 还在 | ✅ **rev173.247 起自检 → 连续 3 次（15 s）后 reload 一次**（见下） | `useMainWindowRescue`（新） |

### 本轮实测（桌面 dev · CDP 对照实验）

只改 **label 前缀** 一个变量：

| 窗口 | label | `Page.crash` 后 40 秒 |
|---|---|---|
| A | `crash-test`（不在守护白名单） | **target 仍在**（`Runtime.enable` 超时 = 渲染进程已死、页面无响应） |
| B | `note-99`（在白名单） | **被清掉**（`/json/list` 只剩主窗口） |

⇒ 崩溃本身**不**关窗口；关掉它的是主窗口的 reaper。所以 `Page.crash` 正是兜底要处理的形态，
不是「兜底覆盖不到」的情形。另：wry / tauri 都没有监听 WebView2 的 `ProcessFailed`
（`grep ProcessFailed` 在 wry-0.55.1 与 tauri-2.12.3 里零命中）⇒ 渲染进程崩溃时宿主拿不到回调，
能靠的只有「另一个活着的窗口」这条通道 —— 这也说明**为什么清理端必须在主窗口**。

### 原先的缺口：主窗口自己白屏 —— ✅ 已补（rev173.247）

**问题**：`domLooksAlive` 查的是 `.zn-plugin-window` / `.zn-note-window`（子窗口根节点），主窗口不在守护范围；
Rust 看门狗（§2.1）判的是**心跳有没有到**，JS 还活着就一直发心跳 ⇒ 「DOM 没了但 JS 还活」两条通道都够不着。

**补法**（`src/lib/window-guard.ts` + `src/hooks/useWindowGuard.ts` 的 `useMainWindowRescue`）：

| 件 | 做法 |
|---|---|
| 判据 | `mainDomLooksAlive`：`.zn-app` 在 + `rect` 宽高 > 0 + 有子元素（与子窗口同一套，只换根节点） |
| 节奏 | 每 5 s 自检一次，**连续 3 次**（15 s）判定没了才动手 |
| 动作 | `location.reload()` —— 整个页面重跑一遍 |
| 防死循环 | `sessionStorage['zn.main-rescue-done'] = '1'`：**一次启动只自救一次**，第二次起放手 |
| 范围 | 只在主窗口（`enabled = !standaloneWindow`）。⚠️ 独立窗口里根本没有 `.zn-app`（根节点是 `.zn-note-window`）—— 若误启用会**永远判定白屏**，这条约束不是可选的 |
| 内容保护 | reload 前 `useDocIO` 的 `beforeunload` / `pagehide` 钩子把未落盘内容写进草稿，重启走「恢复草稿」（rev173.65） |

**实测（桌面 dev · CDP）**：

| # | 做什么 | 期望 | 实测 |
|---|---|---|---|
| 1 | `sessionStorage` 清空 → 把 `.zn-app` 设成 `display:none` | 15 s 后页面 reload、`.zn-app` 恢复可见、flag 置 `'1'` | ✅ `height 1080 / display flex`，flag `'1'` |
| 2 | flag 已是 `'1'` 时再设 `display:none` | **不** reload（防原地循环） | ✅ 18 s 后仍 `display:none` |
| 3 | 正常页面挂一个 `window.__probe` 等 20 s | 不刷新（不误救） | ✅ 时间戳未变、flag 仍 null |
| 4 | 独立窗口（`?note=`）里等 20 s | 不参与主窗口自救 | ✅ 时间戳未变、flag null |

**仍然会丢的那一小块（如实写）**：私密笔记的明文不进 `localStorage` 草稿，所以「白屏那一刻正在改私密笔记且没到 800 ms 自动保存」
会丢那一下。要补得给私密笔记单独一条内存态救援通道，成本远大于收益（18 秒白屏 + 恰好正在改私密笔记，概率极低）。
**「内核代码被改坏」那种白屏 reload 也没用** —— 但那种情况本来就归 `修复内核.cmd` 管，且 self-rescue 一次就放手，不会把用户卡在刷新循环里。
