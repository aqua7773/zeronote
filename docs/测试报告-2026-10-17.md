## 1 问题清单

### P1-1 大纲折叠后残留竖线（用户报）

- **现象**：折叠一个「有子项的父行」后，子行消失，但父行下方仍残留一条竖线；折叠/展开来回切换后可能叠加。
- **复现**：
  1. 打开含三层列表的笔记（`_tmp-vault-tb/outline-demo.md`）
  2. 点「一级 A」左侧圆点折叠 → 子行隐藏
  3. 再点「一级 B」圆点折叠 → **B 下方仍有一条竖线**（子行 B1 已不可见）
- **实测证据**：`_shots/test-02-folded.png`（A、B 均折叠后仍有残留线）
  行 class 读数（折叠 A 后）：`… zn-ol-d1 zn-ol-foldable zn-ol-folded` 之后仍出现 `zn-ol-d2`。
  对照（全部展开）：9 行全部正确，末尾空行无 class —— 说明**只在折叠态出错**。
- **根因（静态，已定位到代码）**：
  内核 `src/kernel/editor-marks.ts:485-498` 的 `buildLineClasses` 对**每一行**（`for n = 1..doc.lines`）都生成 `Decoration.line`，
  **没有跳过 `foldedRanges(state)` 已经隐藏的行**。CM6 折叠后这些行的装饰位置被 map 到折叠点附近，
  背景线（`styles.css:1574-1614` 的 `background-image` 画在行盒上）仍会绘制，于是出现"线还在、内容没了"。
- **修复方向**：生成装饰前先算折叠区间，落在区间内的行不生成 `Decoration.line`（一行改动，风险低）。
  注意不要顺手改插件侧 `classAt`（它按行号返回是正确契约）。

### P1-2 `frontmatter` 恒为空对象

- **现象**：`NoteMeta.frontmatter` 声明了类型，但广播文档事件时写死 `{}`；`doc.active()` 同样写死 `{}`。
- **实测/静态**：`src/App.tsx:733`、`src/App.tsx:769` 两处均为 `frontmatter: {}`；Rust 侧 `lib.rs:98` 的 `parse_frontmatter()` **已经解析**，只是没沿 `NoteMeta` 传下来。
- **影响**：标签、创建/更新时间、密级（`docs/archive/1.目录结构.md` 第 2 条明确要求"跟随 md 文件但不在正文内"）**没有任何落点**；插件只能自己重解析正文。
- **修复方向**：Rust `list_notes`/`read_note` 已返回 `frontmatter` 字段 → 前端 `NoteMeta` 透传 → `doc.active()` 与 `on('open')` 用它。

### P1-3 原子写在 rename 失败时先删旧文件（潜在数据丢失）

- **静态位置**：`src-tauri/src/lib.rs:308-315` —— rename 失败分支先 `remove_file(abs)` 再重试 rename。
- **风险**：两步之间崩溃/断电 ⇒ **旧内容已删、新内容未就位**。当前只在"目标已存在且 Windows 不允许覆盖"时触发，概率低但后果是丢笔记。
- **修复方向**：旧的先 rename 成 `.bak` → 新的 rename 到位 → 删 `.bak`（改名三次，任何一步失败都能回退）。

### P1-4 大库列表性能：取标题要全文读每个 `.md`

- **静态位置**：`lib.rs` 的 `list_notes`（`HANDOFF.md` 与说明书均记录：为取标题把每个文件全文读一遍）。
- **影响**：库大（1000+ 篇）时打开/刷新明显变慢；`fs.watch` 的 3 秒轮询会放大（见 P2-5）。
- **未实测**：本次测试库只有 6 篇，**未做千篇级压测**，结论来自代码路径。
- **修复方向**：标题优先取 frontmatter.title → 否则只读前 4 KB。

### P1-5 `daily-note` 未默认启用，新建笔记不落日期目录 —— ⚠️ rev110 后待复验

> 2026-10-17 rev110 加了**内置插件预装**（`src/kernel/builtin-plugins.ts` 含 `daily-note`），
> 此条可能已修；本报告未复验。

- **实测**：在测试库点「新建笔记」（命令面板 / `core.newNote`）→ 文件落在**库根** `untitled-20261017-135215.md`，而规格要求 `笔记/年/月/日/HH-mm-ss.md`。
- **原因**：`daily-note` 插件**没有 junction 到测试库**（`.zn/plugins` 里只有 asset-probe / doc-reader / import-export / net-demo / outline-map）。
- **判断**：不是代码 bug，是**默认装配缺失**——功能做完了，但默认装不上，用户会当成"规格没实现"。
- **建议**：要么把 `daily-note` 设成推荐插件（安装向导默认勾选），要么在 `新建笔记` 时若检测到 `笔记/` 目录就自动落当天目录。

### P2-1 暗色主题下大纲竖线几乎不可见

- **实测读数**：`--zn-ol-line` = `#2e2e33`，背景 `#18181b` ⇒ 对比度约 **1.2:1**（WCAG 非文本对比度建议 ≥3:1）。
- **证据**：`_shots/test-19-dark-fold.png`（深色下竖线几乎看不出）。
- **修复方向**：暗色下把 `--zn-ol-line` 提到 `#3f3f46`（约 1.9:1）或 `#52525b`（约 3:1）。

### P2-2 `[[文件名]]` 点击跳转被编辑器抢占

- **静态**：`@atomic-editor/editor` 自带 wikilink 语法优先于插件 `editor.addMark`，点击被它吃掉。
- **影响**：规格 §2.2「笔记引用与跳转」只差这一步；反链未开工。
- **建议**：与 atomic 上游协商或用 `editor.addLineAction` 绕开（已有能力）。

### P2-5 `fs.watch` 每个订阅者一条 3 秒全库轮询

- **静态**：`src/kernel/fs.ts:99-114` —— `setInterval(..., 3000)` 每订阅者一条，且与事件通道并行。
- **影响**：内核 + N 个插件 = **N+1 次 `list_notes` IPC / 3 秒**；配合 P1-4 的全量读文件，大库会持续占 CPU。
- **建议**：事件通道可用时停掉轮询；或全局共享一条轮询。

- **实测**：`package.json` 全文无这两个字段。换机器 Node/pnpm 版本不对时无提示，只报怪错。
