# 同步插件 · 调研与方案（2026-10-24）

> 状态：**draft（等拍板）**｜发起：用户「做同步插件，先调研，然后列方案」
> 权威依据：需求规格 §2.5 · `decisions/D-002` · 内核契约 v0.2 · 本仓一手实测 · 同类产品官方文档（§4 全部带链接）

## 0 结论速览

1. **同步的难点不是搬文件，是「谁来判断冲突」。** 内核 10 条原语里**没有网络、没有二进制读写、没有库外静默写**（§3），
   插件今天做不到「自己把一个 `.md` PUT 到 WebDAV」，也读不了 PDF/图片的字节。
2. **最省的第一期不是做同步，是做「同步的体检与兜底」**：库放进用户自己的同步目录（OneDrive / Syncthing / 坚果云），
   插件负责 ① 发现外部改动 ② 判定「双端都改」 ③ 冲突留副本 ④ 状态页。**零内核改动，1–1.5 天**（方案 A）。
3. **真要在 App 内直连 WebDAV，必须先给内核一条走 Rust 的 HTTP 通道**（`tauri-plugin-http` 的 fetch
   在 Rust 侧执行，**不受 CORS 约束**，官方原文见 §4.5）。加上二进制读写，**总成本 3–4 天**（方案 B）。
4. **Git 同步只适合桌面**：手机端 isomorphic-git 被作者自己标为 "very unstable"（§4.4），不做主线（方案 C）。
5. 需求 §2.5 里的「实时自动同步 / 扫码配置 / 大文件按需同步」**本期不做**，理由逐条见 §7。

## 1 需求原文与历史决策

需求规格 §2.5（`docs/archive/Markdown 笔记应用需求规格 v1.0.md:208-228`）：

- 实时自动同步
- MVP 支持：**WebDAV** + **本地文件夹同步**（用户可配 Syncthing / OneDrive / 网盘等）
- 扫码配置后置
- 冲突：正常以最新为准；**双端离线修改时生成冲突副本**（不弹窗阻塞），副本按平台分文件夹
- 同步状态页：进度、大文件提示、错误信息

`D-002`（2026-10-17，accepted）当时结论是「不做账号 / 服务器 / 云同步，同步交给用户自己的网盘」，
重议条件 =「多设备冲突成为真实痛点，且明确接受『冲突文件』语义」。
**本次正是该重议**：只做客户端侧的同步能力，不做服务端、不做账号。

## 3 三个技术缺口（方案边界由它们决定）

1. **网络**：WebDAV 的 `PROPFIND`/`PUT` 不是简单请求，必然触发 CORS preflight（`OPTIONS`）；
   服务器不回 CORS 头就一律失败，插件侧只能看到 `TypeError: Failed to fetch`，**分不清是 CORS、断网还是 401**
   （2026-10-12 踩过一次，见 `插件能力盘点` 的更正段）。⇒ 要么走 Rust，要么不直连。
2. **二进制**：同步必须覆盖图片附件与 PDF/EPUB；`fs` 只有文本。`copy` 能复制但不能读写内容（做不了「下载字节 → 写文件」）。
3. **库外静默写**：把笔记镜像到另一个目录需要静默写库外，现有 `host.saveFile` 每写一个文件弹一次对话框。

## 4 同类做法（一手来源）

### 4.1 Joplin —— 抽象驱动 + item 级 + updated_time 判据
- 同步目标：Joplin Cloud / Nextcloud / S3 / WebDAV / Dropbox / OneDrive / 本地文件系统，
  统一成「类文件系统」驱动（read / write / delete / list），换服务只换驱动。
- 流程是 **item 级**：改动后数秒内上传该 item，下载按固定间隔（几分钟）轮询 —— **冲突多发生在下载间隔内**。
- 冲突判据：item 的 `updated_time`。默认 `sync.autoMergeConflicts` 会用 base/local/remote 三路行级合并；
  合不了才落冲突副本。
- 冲突副本：新建一条 note（**标题不变**，新 id，标 `is_conflict=1` + `conflict_original_id`），
  远端版本替换本地。
- 删除：`deleted_time` 软删除 + 删除记录传播。
- 来源：https://joplinapp.org/help/apps/sync/ · https://joplinapp.org/help/dev/spec/sync · https://joplinapp.org/help/dev/spec/conflict_auto_merge

### 4.2 Obsidian Sync —— 文件级、默认自动合并、冲突文件是可选项
- 文件级同步，按文件大小给上限（Standard 5 MB / Plus 200 MB）。
- 冲突：Markdown 默认 **diff-match-patch 自动合并**；其它文件 last-modified-wins；设置文件按键合并。
- 1.9.7+ 可选「Create conflict file」，命名 `笔记名 (Conflicted copy 设备名 YYYYMMDDHHMM).md`。
- E2EE 默认（AES-256-GCM / scrypt），订阅制 $4/用户/月。
- 来源：https://obsidian.md/help/sync/troubleshoot · https://obsidian.md/help/sync/security · https://obsidian.md/help/sync/plans

### 4.3 Syncthing —— 块级传输 + 文件名后缀
- 文件切块（128 KiB–16 MiB），每块 SHA256，只传变化的块。
- 冲突条件：同文件两台设备都改且内容不同 ⇒ **mtime 较旧的那个**改名为
  `<文件名>.sync-conflict-<日期>-<时间>-<设备>.<扩展名>`；mtime 相同则 device ID 较大者被标冲突。
- 冲突副本按普通文件继续传播；删除 vs 修改冲突时，删除赢也会把文件改名成冲突副本。
- 来源：https://docs.syncthing.net/users/syncing.html

### 4.4 obsidian-git —— Git 冲突靠编辑器 UI
- 定时 commit + pull + push；启动先 pull。
- 同文件两端修改 = 真 Git merge 冲突，插件只做 UI（keep ours / theirs / both），不做语义合并。
- **移动端用 isomorphic-git，作者自述 "very unstable"**，无 SSH、无 rebase、有内存限制。
- 来源：https://github.com/Vinzent03/obsidian-git

### 4.5 Tauri 2 的 HTTP 客户端 —— 绕 CORS 的正路
- `@tauri-apps/plugin-http` 的 `fetch` **在 Rust 侧（reqwest）执行**。官方 API 文档原文：
  > "The request is performed by the Rust backend instead of the webview, so **it is not subject to CORS**,
  > but the URL must be allowed by the plugin scope."
- 平台支持：Windows / Linux / macOS / **Android** / iOS 全绿；要求 Rust ≥ 1.90；权限在 capabilities 里用
  `http:default` + URL glob 白名单声明；CSP 也要放行对应 host。
- 维护者在 issue 里的一句话佐证：「using Tauri's http api may help since its executed on the rust side where cors isn't a thing」。
- 来源：https://v2.tauri.app/reference/javascript/http/ · https://github.com/tauri-apps/tauri/issues/11260

### 4.6 WebDAV 直连在浏览器里的现实
- `PROPFIND` 不是简单方法（简单方法只有 GET/HEAD/POST）⇒ **必触发 preflight**；`PUT` 带自定义头也 preflight。
- Nextcloud issue #3131（2017 开、至今 open）：*"Currently this is not possible as the necessary CORS headers are not set."*
- 坚果云官方帮助中心没有 CORS 相关说明（未找到一手来源证明其返回 ACAO）。
- 来源：https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request · https://github.com/nextcloud/server/issues/3131

## 5 候选方案

### 方案 A（推荐第一期）：同步体检 + 冲突兜底 `sync-guard`
**不搬运文件**：库放进用户自己的同步目录，搬运交给 OneDrive / Syncthing / 坚果云。
插件只做三件事：发现外部改动、判定双端都改、冲突留副本。

- 数据：`store` 里 `baseline: { [path]: { hash, mtime, savedAt } }` + `device`（windows/android）
- 判定：
  1. `note:saved` ⇒ 更新 `baseline[path] = { hash, mtime, savedAt: now }`
  2. `note:changed`（外部改动，内核已过滤自写）⇒ 该 path 在基线里且 hash 变了：
     - `savedAt` ≤ 基线时间 ⇒ 只是别处更新 ⇒ 接受，刷新基线
     - `savedAt` > 基线时间 ⇒ **双端都改** ⇒ 冲突
  3. 冲突 ⇒ 从 `.zn/history/` 取该篇最近一份「冲突前快照」，`fs.copy` 成
     `冲突/<windows|android>/<YYYY-MM-DD HHmm>-<文件名>`；toast + 面板记录（不弹窗阻塞）
  4. 删除 vs 修改：外部删、本地改过 ⇒ 本地版留成冲突副本；本地删、外部改 ⇒ 恢复外部版
- 面板 `sync.status`（主区标签）：最近外部改动时间 · 冲突列表（点击跳转）· `.zn/` 是否被同步工具同步
  （若收到 `.zn/` 内的外部改动事件 ⇒ 警告「同步工具正在同步私有目录」）· 同步建议（排除 `.zn/`、`_shots/`）
- 能力：`fs` `store` `event` `view` `command` `host`（可选 `service` 调 `history`）
- **成本：1–1.5 天**（插件一个，不动内核）
- 验收：造两个库副本模拟两端 → 改同一篇 → 手动覆盖触发 → `冲突/windows/...` 出现且内容 = 本地版 ·
  状态页数字对 · 单测覆盖判定函数（四类场景）· 手机端同一套（3 秒轮询）
- 局限：同步本身依赖第三方工具；手机要装 Syncthing（SAF 选目录有摩擦）；冲突是「事后发现」

### 方案 B（第二期，要手机端独立同步时）：WebDAV 直连 `sync-webdav`
- 前提：内核先有一条**走 Rust 的 HTTP 通道**。三种实现，推荐 B-1：
  - **B-1**：内核加 `host.http()` 原语（契约 v0.3），内部调 `plugin:http|fetch`；
    scope 用 capabilities 的 `http:default` + 用户配置里声明的 DAV 域名（运行时拼不进静态 capability ⇒
    退一步允许 `https://*`，在设置页写明「同步插件可访问任意 https 地址」）
  - B-2：内核自己写一条 Rust `http_request` 命令（reqwest 直连，scope 自控）
  - B-3：插件直接 `__TAURI_INTERNALS__.invoke('plugin:http|fetch')`（**不推荐**：绕过契约，等于给所有插件开后门）
- 同时补二进制：`fs.readBytes` / `fs.writeBytes`（或让 `host.http` 直接支持 base64）
- 插件：WebDAV 客户端（PROPFIND / GET / PUT / DELETE / MKCOL）· 凭据存 `store`（**明文风险要写给用户**）
  或系统钥匙串（Rust 侧 `keyring` crate）· 远端 etag/mtime 表 · 双向循环 · 冲突副本（复用 A 的判定）
- **成本：内核 0.5–1 天 + 插件 2–3 天 = 3–4 天**
- 风险：凭据安全 · 坚果云限流（免费 600 次/30min，付费 1500）· 大文件超时 · 各家 WebDAV 行为差异
- 验收：本地 Nextcloud sandbox 两端同时改同一篇 → 冲突副本 · 5 MB 附件往返 · 断网重试 · Android 真机

### 方案 C（不推荐主线）：Git 同步
- 桌面：Rust 调外部 `git`（或加 `proc` 能力），定时 commit+push；冲突 = Git merge。
- 手机：isomorphic-git 作者自述 very unstable ⇒ 不做。
- **成本 1.5 天（桌面 only）**，收益不大。

### 方案 D（不做）：自建服务端 / 账号 / E2EE
违背 `D-002` 与产品定位（无服务器、数据就是文件）。E2EE 只在 Obsidian 那种「有云端」的场景才有意义。

## 6 冲突语义（这是 D-002 的卡点，必须先定）

| 场景 | 判定 | 处理 |
|---|---|---|
| 只有本地改 | `savedAt` 更新、无外部事件 | 无动作 |
| 只有外部改 | 外部事件 + 本地 `savedAt` ≤ 基线 | 接受，刷新基线 |
| **双端都改** | 外部事件 + 本地 `savedAt` > 基线 | 原路径保留外部版；本地版（取 `.zn/history/` 最近快照）写到 `冲突/<平台>/<时间>-<文件名>`；toast + 面板 |
| 外部删 / 本地改 | 外部 delete + 本地 `savedAt` > 基线 | 本地版写成冲突副本（恢复一份） |
| 本地删 / 外部改 | 本地 delete 在外部改动后 | 接受外部版（恢复文件） |
| 改名 | path 变化 | 视为 delete + create（不跟 rename，成本不值） |

命名对齐需求「按平台分文件夹」：`冲突/windows/2026-10-24 1832-周报.md`。
**待定**：冲突目录放库内（会被同步工具再同步）还是 `.zn/conflicts/`（不参与同步、换设备看不到）。

## 7 成本、验收与本期不建议做的部分
