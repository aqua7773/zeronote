# ZeroNote 文档编写规范

> 状态：**active** ｜制定：2026-10-17（rev93）｜权威范围：本文管"文档怎么写"；软件安装 / 删除 / 系统改动仍按本机 `~/.dsh/AGENTS.md`

---

## 0 一条总原则

**每份文档只回答一类问题；同一事实只在一个地方写"当前值"，其他地方引用它。**

推导出来的三条禁令：

1. 不把易变计数（测试数、插件数、行数）硬编码进多份文档；
2. 不在"历史记录"里混写"当前状态"；
3. 不让两份文档同时声称自己是权威。

---

## 1 先选层，再动笔

| 层 | 放什么 | 例子 | 生命周期 |
|---|---|---|---|
| **入口** | 现状 + 怎么跑 + 文档地图 | `README.md` | 长期，随功能更新 |
| **权威** | 为什么这样设计 / 接口是什么 | `docs/架构原则-*.md`、`docs/内核契约-*.md` | 长期，改前要用户同意 |
| **需求** | 目标是什么（唯一） | `docs/requirements/current.md` | 长期，变更走取代 |
| **记录** | 逐版本做了什么 + 证据 | `HANDOFF.md`、`HANDOFF-CARD.md` | 只追加，不改历史 |
| **方案/调研** | 一次决策的论证过程 | `docs/*-调研-*.md`、`_research/*` | 落地后转 historical |
| **用户文档** | 给最终用户的操作步骤 | `docs/Android安装说明.md` | 随版本更新 |
| **过程产物** | 打包日志、截图、临时脚本 | `_build/`、`_shots/`、`_tmp-*/` | 可删可重建 |

判断口诀：**"这篇是在回答『为什么』『是什么』『到哪了』还是『怎么做』？"** 只回答一类。

## 2 状态头（每份文档必须有）

正文开头 5 行内，用引用块写：

```markdown
> 状态：**active** ｜最后核对：2026-10-17 ｜权威范围：<一句话>
```

四种状态，只用这四个词：

| 状态 | 含义 | 允许被引用为"现状"吗 |
|---|---|---|
| **active** | 当前有效 | ✅ |
| **superseded** | 已被另一份取代，保留作历史 | ❌（必须写"取代者：X"） |
| **historical** | 一次性素材 / 调研快照 / 旧方案 | ❌ |
| **draft** | 未定稿，随时可改 | ⚠️ 只能内部讨论用 |

superseded / historical 的写法：

```markdown
> 状态：**superseded**（被 `docs/requirements/current.md` 取代，保留作历史）｜最后核对：2026-10-17 ｜取代者：current.md
```

> active 文档的"最后核对"超过 **7 天** 且这期间代码有变更 ⇒ 视为**待核对**，引用前先抽查。

## 3 单一事实源（SSOT）

| 事实 | 唯一来源 | 其他文档怎么写 |
|---|---|---|
| 四条验收基线（tsc / oxlint / cargo / vitest） | `scripts/verify.ps1` 的输出 | 「以 `scripts\verify.ps1` 输出为准」；需要举例时注明日期 |
| 版本号（Tauri / React / Vite…） | `README.md` 技术栈表 | 引用 README，不复制 |
| 插件数 / 文件数 / 行数 | 统计命令（写进报告或 `_build/README`） | 写「约 N」+ 统计方法；不写死 |
| 需求目标 | `docs/requirements/current.md` | 旧需求标 superseded |
| 接口签名 | `src/kernel/contract.ts` | 契约文档写"对应 contract.ts"，行号标"写作时" |
| 当前状态 / 下一步 | `HANDOFF-CARD.md` | 其他文档不重复"下一步" |

**基线数字示例（正确写法）**：

```markdown
| 基线 | 以 `pwsh -File scripts\verify.ps1` 的输出为准（2026-10-18：tsc 0 · oxlint 6 · cargo 27 · vitest 44） |
```

**错误写法**：在 5 份文档里各写一个数字，改一处忘四处。

## 4 事实标注

- **`文件:行号` 只写已核实的**。行号会漂移 ⇒ 写「（写作时）」或在段首标核对日期。
- **事实 / 判断 / 建议分开**：
  - 事实：带 `文件:行号`、命令输出、截图路径；
  - 【推测】：未核实的原因；
  - 【判断】/【建议】：我的取舍，不是代码里的事实。
- **否定性结论**（"不可行 / 已删除 / 已失效"）必须有证据，并写明核实日期。宁可写"未核实"，不许写"应该没问题"。
- **未核实项单独成节**，标题统一为「未核实」或「未验」，不混进结论表。

## 5 HANDOFF 写法（rev 记录）

### 5.1 标题格式

```
> ## 📌 revNN（YYYY-MM-DD · 一句话结论）
```

### 5.2 每条 rev 必须有三段

1. **做了什么**（含落点文件 / 命令）
2. **证据**（截图路径、实测读数、命令输出；没有证据就写"未验证"）
3. **未做 / 边界**（防止下一个人误以为都做完了）

### 5.3 位置与索引

- 新 rev **追加在 rev 索引之后、当前第一个 rev 段之前**（保持"最新在前"）；
- 同时更新文首的 `| revNN | 内容 |` 索引行与 `revision:` 行；
- 段与段之间空一行，段落内部保持 `> ` 引用块。
- **分卷（2026-10-25 · rev173.139 起）**：`HANDOFF.md` 只保留**当前版本周期**的 rev（默认最近 14 个），更早的按版本在 `docs/archive/handoff/`（`0.2.md` / `0.3.md` / `0.4.md` …）。
  新版本发版后跑 `node scripts/handoff-archive.mjs` 把上一代切出去（幂等，已归档的卷自动跳过）；
  **分卷必须同时切索引表与正文段** —— `check-docs` 第 ③ 条要求两者 rev 集合完全一致。
  归档文件是只读历史，不参与 `check-docs` 的索引检查，但**参与 `check-links`**（`docs/**` 全递归）。

### 5.4 更正旧结论

在**原文处**标 `⚠️ 更正见 revXX`，不许只在新段落里说——否则下一轮读到旧段落又会当真。

### 5.5 HANDOFF-CARD 的边界

只放：当前状态 / 未决问题 / 唯一下一步 / 环境速查。
**细节一律回 HANDOFF**；卡超过 120 行就是把该放 HANDOFF 的东西塞错了地方。

## 6 命名与目录

| 类型 | 路径 | 例子 |
|---|---|---|
| 长期规范 | `docs/<主题>.md`（无日期） | `architecture.md`、`contract.md` |
| 有日期的快照 / 方案 | `docs/<主题>-YYYY-MM-DD.md` | `卡死兜底方案-2026-10-13.md` |
| 需求 | `docs/requirements/current.md`（当前）· `requirements/history/`（旧） | — |
| 决策记录 | `docs/adr/NNN-短标题.md` | `adr/001-文件即真源.md` |
| 调研 | `_research/<主题>-YYYY-MM-DD.md` | `插件API对比.md`（缺日期，历史遗留） |
| 用户文档 | `docs/guides/<主题>.md`（目标） | `android-install.md` |

链接一律用**仓内相对路径**（`docs/...`），不写 `C:\Users\...` 绝对路径（本机环境说明除外）。

## 7 ADR（架构决策记录）写法

一个决定一篇，四段固定：

```markdown
# ADR-NNN：<决定一句话>

> 状态：accepted ｜日期：YYYY-MM-DD ｜相关：revXX / HANDOFF

## 背景
（为什么要做这个决定；约束是什么）

## 选项
（A / B / C，各一行代价）

## 决定
（选了什么，为什么）

## 后果
（正面 / 负面 / 需要后续做什么）
```

适合进 ADR 的：数据真源、插件不设防、沙箱搁置、编辑器选型、同步路线。
**不要**把每个 rev 都写成 ADR —— rev 是流水账，ADR 是里程碑。

## 8 长度与可读性

| 文档 | 上限 | 超了怎么办 |
|---|---|---|
| 入口 README | 150 行 | 细节挪 docs，留链接 |
| 交接卡 | 120 行 | 细节回 HANDOFF |
| 单份规范 | 300 行 | 拆子文档 |
| HANDOFF 单条 rev | 80 行 | 拆成 rev + 独立调研/方案 |

写法要求：

- 每节第一句给**结论**（"结论：…"），细节放表格；
- 表格优于长段落；数字优于形容词；
- 读者只有 1 分钟时，能从"文档头 + 每节首句"拿到：现状、下一步、去哪读。

## 9 改完同步什么（checklist）

| 改了什么 | 必须同步 |
|---|---|
| 契约 | `contract.ts` + 契约文档 + 升版本 + CHANGELOG（建立后） |
| 架构 / 原则 | 架构原则 + 所有相关方案文档的状态头 |
| 基线 / 依赖 | `scripts/verify.ps1` + 卡里基线行（只引用输出） |
| 新增 / 删除文档 | `docs/README.md` 权威矩阵 + `README.md` 文档地图 |
| 需求变化 | `requirements/current.md`；旧需求标 superseded |
| 行为变化 | HANDOFF 新 rev + 卡的状态 |
| 用户可见流程 | 对应用户文档（如 Android 安装说明） |

## 10 发稿前自查（30 秒）

- [ ] 状态头存在，日期 ≤ 7 天（active 文档）
- [ ] 没有手写易变数字（测试数 / 插件数 / 行数）
- [ ] 抽验 3 处 `文件:行号` 引用
- [ ] 否定性结论都有证据 + 核实日期
- [ ] 新增文档已进 `docs/README.md` 与 `README.md` 文档地图
- [ ] 没有无日期、无状态的"孤儿文档"
- [ ] 跑过 `node scripts/check-docs.mjs`（契约 vs 代码 / 状态头 / 索引 / 引用）

---

## 11 边界

本规范只管**文档**。软件的安装位置、删除前检查、系统改动、回退快照，仍按本机 `~/.dsh/AGENTS.md` 与 `Apps/README.md` §0 执行。
