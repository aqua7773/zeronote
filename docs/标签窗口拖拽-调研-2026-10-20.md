## 结论先行

1. **主流应用的「拖回」拖的是标签，不是窗口**：Obsidian、Chrome / Edge 都是把**标签**拖到目标窗口上，
   拖动期间源窗口持有指针捕获、能拿到全局坐标（`screenX/screenY`），与**目标窗口矩形**求交决定落点。
   拖出所有窗口 = 拆成新窗口；拖到目标窗口 = 并进去，拖动中还显示 drop zone 高亮。
2. **「拖窗口本身让它合并吸附」没有通用能力**：Windows 只有屏幕边缘 Snap（系统级），没有「窗口互相吸附合并」。
   纯自研只能 `onMoved` 事件 + 窗口矩形判定（或全局钩子），而且没有同品类先例可抄。
3. Tauri 2 的 API 够用：`onMoved` / `outerPosition` / `outerSize` / `getAll` / `getByLabel` / `setPosition` / `startDragging`。
   生态里的 `tauri-plugin-snap-layout` **不适用** —— 它是 Win11「最大化按钮悬停出 Snap Layout」，
   靠 Win32 子窗口 `WM_NCHITTEST` 返回 `HTMAXBUTTON`，与两个窗口合并无关。

## 机制归纳（两种判定，差在「拿不拿得到指针」）

| 形态 | 指针可见性 | 判定方式 | 代表 |
|---|---|---|---|
| **拖标签**（页内元素） | 拖动全程有（源窗口捕获鼠标） | `screenX/screenY` + 目标窗口矩形求交；可精确到「目标窗口的标签栏」 | Obsidian、Chrome |
| **拖窗口**（系统窗口） | 页面收不到 | `onMoved` 事件（或轮询）读双方 `outerPosition/outerSize`，启发式判重叠 | Windows Snap（系统级）、FancyZones 类工具 |

## 我们的现状（rev173.50–53）

- 主窗口：拖标签**出界**（6 px 热区）⇒ `openInWindow` 拆成独立窗口；右键菜单同效。
- 独立窗口：只有编辑器 + 标题条（用户要求「只要编辑窗口」），收回 = 标题条左侧 `⤺` 按钮。
- **缺口**：独立窗口里没有可拖的东西 ⇒ 没有「拖回」手势。

## 三条可走的路

### A. 独立窗口加回一条「把手标签」（与 Obsidian / Chrome 同构）

- 拖这条标签到**主窗口任意位置** → 松手收回（拖动中标签高亮、提示「松手 → 收回主窗口」）。
- 判定：`pointerdown` 时缓存 `WebviewWindow.getByLabel('main')` 的 `outerPosition/outerSize`；`pointerup` 用 `screenX/screenY` 判是否落在主窗口矩形内。
- 成本：2 个窗口权限（`allow-outer-position` / `allow-outer-size`）+ 约 80 行；判定精确，无轮询。
- 代价：编辑窗口顶部多一条 34 px 标签（与上一轮「只要编辑窗口」的要求冲突）。

### B. 拖标题条（窗口本身）越过本窗口边界 = 收回

- 与主窗口的「拖出标签 = 拆出」**对称**：拖出本窗口边界 ⇒ 收回主窗口。
- 判定复用现有 `isOutsideWindow`（`src/lib/tab-drag.ts`），不需要主窗口矩形、不需要新权限。
- 成本：约 40 行（标题条指针拖拽 + 越界判定）。编辑窗口保持干净。
- 代价：没有「目标窗口高亮」；这是自定义手势，用户要知道「拖标题条出界 = 收回」。

### C. 拖窗口到主窗口上 → 自动吸附（最接近字面「拖回去」）

- 事件驱动：`onMoved` + 250 ms 静止（debounce）判定；独立窗口与主窗口**顶部 34 px 标签栏区域**相交 ⇒ 吸附。
- 成本：`allow-outer-position` / `allow-outer-size` 权限 + 约 80 行；需要调参。
- 代价：**误吸附**（把窗口叠在主窗口顶部附近会被吸走）；没有同品类先例，是自研启发式。

## 建议

- 想要「拖到主窗口上松开就回来」的确定感、又能接受一条把手：**A**（与主流一致）。
- 想保持「编辑窗口只有编辑器」：**B**（零权限、与现有手势对称）。
- 坚持「拖窗口本身自动吸」：**C**，但只认主窗口顶部标签栏区域，别用整个窗口，否则误吸附会很烦。

> 三者互不排斥；A/C 可以共用同一个 `returnToMain`（保存 → 通知主窗口 → 关窗），B 也是同一条动作。

### 我们的具体差别（代码事实，不是推测）

- **插件在每个窗口都加载**：`App` 无条件调 `usePluginHost`，而其中会跑 `ensureBuiltinPlugins(globalRoot)`（写盘检查）+ 扫描；内置 5 个插件里 4 个没有 `activationEvents`、`accounting` 是 `onStartup`，所以它们每个窗口都会执行代码（声明了懒激活的用户插件只登记命令）。
  （`src/hooks/usePluginHost.ts:196` 附近，没有窗口判断）。内置插件的副作用（store 写入、JS 监听）会随窗口数量成倍；通知捕获在原生 Kotlin 服务，只有一份。
- **每个窗口一份内核与索引**：`createKernel` 每窗口新建；`index.rebuild()` 由搜索面板打开时触发，也是每窗口各自一份。
- **互斥账本在主窗口内存**（`noteWindowsRef`）：主窗口 reload（dev HMR）就丢，已开的独立窗口从此"失联"。
- **文档状态不共享**：每个窗口独立 React state，靠 `fs.watch` + 三方合并兜底（同一篇两边开会有合并提示）。

### 可改进（按成本从低到高）

1. **笔记窗口跳过插件加载**：编辑器与 Markdown 渲染是内核能力（`src/kernel/editor-*`），不依赖插件；给 `usePluginHost` 加 `noteWindowPath` 条件即可去掉重复副作用与一部分启动成本。插件窗口（`?pluginWindow=`）仍要加载。
2. **占用账本搬到 localStorage 或 Rust `app.manage`**：窗口无关，主窗口 reload 也能恢复；顺带能实现「重启后还原打开的独立窗口」。
3. **真正的共享插件宿主**（VS Code 模式）：插件宿主进 Rust 或独立进程，窗口只做视图 —— 成本大，不在当前这条线上。

> 第 1 条同时解决一个隐患：插件若在窗口里重复注册命令 / 监听事件，行为是「两边各触发一次」。
