## 0 先问一个问题：市场是给谁用的

这决定了值不值得做，比怎么做更重要。

| 场景 | 现在怎么装 | 市场解决什么 | 值不值 |
|---|---|---|---|
| **只有你自己** | `.znp` 双击 / 拷文件夹 | 几乎没有 —— 目录就在本机，`examples/` 里全是源码 | ❌ 净成本 |
| **给第二个人用** | 你发 `.znp`，对方「插件管理 → 安装插件包」 | 不用先知道名字、不用被微信压缩包搞坏 | ✅ 唯一价值 |
| **手机端** | 长按选文件（MIUI 的 SAF 对未知扩展名很挑，rev119 踩过） | **一键装** —— 手机上这是体验差距最大的一环 | ✅ 价值最大 |

**结论**：市场对「自用」是负担，对「分发」和「手机」是刚需。
`D-008` 当时降级的真实理由是「唯一用户就是作者」——**如果开源/分享的计划变了，这个理由就失效了**，本文就按「会分发给别人」来设计。

## 1 现在已经有什么（逐条核实）

| 能力 | 落点 | 状态 |
|---|---|---|
| `.znp` 单文件 JSON 包（`{znp:1, manifest, files:{名:内容}}`） | `src-tauri/src/lib.rs` `read_znp` / `install_znp` | ✅ |
| 解包到全局插件根 + 路径穿越防护（`plugin_file` 白名单） | 同上（有 `install_znp_rejects_path_escape` 单测） | ✅ |
| 完整性：`manifest.sha256` | 加载前比对，不符拒载 | ⚠️ **只覆盖入口一个文件** |
| **Ed25519 真签名** + Rust 验签（`ed25519-dalek`） | `src/lib/plugin-signing.ts` · `lib.rs` `verify_plugin_signature` | ✅ |
| 信任根 `.zn/trusted-keys.json` | 手工放 | ⚠️ **没有分发渠道** |
| 插件页（分组 / 开关 / 版本 / 来源 / 删除 / 日志） | `src/components/PluginPanel.tsx`（323 行） | ✅ |
| 网络原语（Rust `reqwest` 绕 CORS） | `ctx.net.fetch`（rev173.106） | ✅ |
| 内核命令 | 33 条（`core.save` / `core.search` / `core.plugins`…） | ❌ **没有任何安装 / 重扫 / 市场相关命令** |

**签名载荷**：`zn-plugin-v1|<id>|<version>|<入口文件 sha256>` —— 由宿主重算，不信 `signature.json` 里的其它字段。

**`.znp` 的结构决定了分发方式**：它是**一个 JSON 文件**，不是 zip。所以「市场」只需要给一个 **URL**，不需要 Release 里挂三个附件。

## 2 参照：Obsidian 怎么做的（一手，2026-10-25 抓）

来源：[obsidian-releases README](https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/README.md) · [community-plugins.json](https://raw.githubusercontent.com/obsidianmd/obsidian-releases/master/community-plugins.json)

**索引就是仓库里一个静态数组**，每条只有 5 个字段：

```json
{ "id": "obsidian-git", "name": "Git", "author": "Vinzent",
  "description": "Integrate Git version control …", "repo": "vinzent03/obsidian-git" }
```

**没有 version 字段** —— 版本在运行时向插件自己的 GitHub 仓库问：

| 步骤 | 做法 |
|---|---|
| 列表 / 搜索 | 读 `community-plugins.json`（`name` / `author` / `description` 参与搜索） |
| 详情页 | 从**插件自己的 GitHub 仓库**拉 `manifest.json` + `README.md` |
| 判断最新版 | 仓库根的 `manifest.json` |
| 安装 | 找与 `manifest.version` **同名 tag 的 Release**，下载 `manifest.json` / `main.js` / `styles.css` |
| 版本兼容 | 运行版本太高 ⇒ 查 `versions.json` 找最后一个兼容版本 |
| 安全 | **没有签名**。靠人工 PR 审核 + developer policies + 首次启用时的风险提示 |

**三条可复用的结论**：

1. **市场不需要服务端** —— 一个静态 JSON + 每个插件自己的托管就够了，Obsidian 全球几千个插件就是这么撑着的。
2. **别在索引里存版本号** —— 版本是插件的属性，存进索引就会和真实发布漂移（Obsidian 选择每次去问）。ZeroNote 的插件都在**本仓库 `examples/`**，这条可以反过来用：索引由脚本从 manifest **生成**，不可能漂移。
3. **Obsidian 没有签名** —— 这是 ZeroNote 已有的优势，别丢。

## 3 ZeroNote 差什么（这决定了改动面）

| # | 缺口 | 影响 | 位置 |
|---|---|---|---|
| 1 | **没有远端索引** | 应用不知道「世界上有哪些插件」 | 新增 `market/index.json` |
| 2 | **没记「这个插件从哪来的」** | 更新通道无法知道去哪查新版 | `manifest.json` 需要加可选字段 |
| 3 | **内核没有安装 / 重扫命令** | 插件自己装不了自己（`ctx.fs` 全部是**库内**相对路径，插件根在 `appDataDir()/.zn/plugins/`，插件够不着） | 需新增 1 条命令 |
| 4 | **信任根是手工放的** | 市场分发的包要验签，公钥从哪来？ | 需预置 |
| 5 | **签名只覆盖入口文件** | 多文件插件（`manifest.files`）里 `lib/*.js` 可被替换而签名仍通过 | `plugin-signing.ts` 的 payload |
| 6 | 手机端拿 `.znp` 难 | SAF 对未知扩展名挑食 | 市场面板直接解决 |

> #3 是硬约束：**没有它，市场只能做成内核功能，做不成插件**。如果希望市场本身是个插件（可被禁用/替换），必须先补这条命令。

## 4 方案

### 4.1 方案 A：静态索引 + 一键装（推荐，先做这个）

```
你的仓库                                    用户的应用
┌────────────────────────┐                ┌──────────────────────────┐
│ market/index.json      │  GET(静态)     │ 市场面板                 │
│  ├ 由脚本生成，不手写  │ ─────────────▶ │  列表 / 搜索 / 详情      │
│  └ 可选 index.json.sig │                │         │ 点「安装」      │
│                        │                │         ▼                │
│ Releases/*.znp         │  GET(一个文件) │  core.plugins.install    │
│  └ 每个包自带 signature│ ─────────────▶ │   校验 sha256 + 验签     │
└────────────────────────┘                │   → install_znp(bytes)   │
                                          │   → 重扫 → 列表里出现    │
                                          └──────────────────────────┘
```

**索引 schema（草案）**

```jsonc
{
  "schema": 1,
  "updated": "2026-10-25",
  "plugins": [
    {
      "id": "tag-panel",
      "name": "标签面板",
      "author": "aqua7773",
      "description": "全库标签按篇数降序，点标签看该标签下的笔记",
      "category": "tool",
      "platforms": ["desktop", "android"],
      "repo": "aqua7773/zeronote",
      "versions": [
        {
          "version": "0.2.0",
          "apiVersion": "^0.2.0",
          "url": "https://github.com/aqua7773/zeronote/releases/download/plugins-v0.2.0/tag-panel.znp",
          "sha256": "<整个 .znp 文件的 sha256>",
          "size": 8214
        }
      ]
    }
  ]
}
```

**改动清单与成本**

| 改动 | 位置 | 成本 |
|---|---|---|
| 生成索引的脚本（合并 `market/entries/*.json` 与 `market/external.json`，跑进质量门防漂移） | `scripts/gen-market.mjs` ✅ rev173.143 | 2 h |
| 打包脚本（目录 → `.znp`，签名，算整包 sha256，产出市场条目） | `scripts/pack-plugin.mjs` ✅ rev173.143 | 1.5 h |
| Rust：`install_znp` 增加「从 bytes 装」入口（复用现有解析与路径防护） | `src-tauri/src/lib.rs` | 1.5 h |
| **`install_znp` 改成原子**：先解到临时目录 → 全部成功再换目录（现在是覆盖写同名文件，半截包会污染现有插件） | `src-tauri/src/lib.rs` | 0.5 h |
| 新内核命令 `core.plugins.install`（url + 期望 sha256 → 下载 → 校验 → 装 → 重扫） | `src/App.tsx` + Rust | 2 h |
| 市场面板 UI（列表 / 搜索 / 详情 / 安装按钮 / 已装态） | `src/components/PluginPanel.tsx` 加一段或新面板 | 4 h |
| 手机端走查（真机 33b676f6） | — | 1 h |
| **合计** | | **≈ 1.5 天** |

**这一版不做**：更新检查、自动升级、卸载回滚、评分评论、搜索后端。

### 4.2 方案 B：A + 更新通道

在 A 之上加：

- 装的时候把**来源**写进插件目录（`market.json`：`{source, repo, version}`），更新检查才有地方问
- 启动时（或手动点「检查更新」）拉索引，比对已装版本
- 有新版的插件在列表里显示 `↑ 0.3.0`，点一下走和安装同一条链路（覆盖安装）
- **不做静默升级**：本项目的插件代码能读任意文件、能 invoke 任意命令（契约 §4.2），替换代码必须让用户看见

| 改动 | 成本 |
|---|---|
| `market.json` 落盘 + 读回 | 1 h |
| 版本比较 + 更新列表 UI | 3 h |
| 覆盖安装路径（`install_znp` 已经是「覆盖写同名文件、不删旧文件」—— 但**删附加文件**需要新增语义） | 1 h |
| **合计** | **+ 0.5 天** |

### 4.3 方案 C：服务端市场（不做）

要账号、要托管、要审核队列、要处理垃圾/举报 —— 与 `D-009`（自带后端、不做服务端）直接冲突。
**除非**将来有明确的多作者需求，否则不碰。

### 4.4 形态：入口在哪、装和更新长什么样（2026-10-25 补）

**结论先说：市场不是新页面，是「插件管理页」里的第二个 tab。**

理由三条：
1. 用户的心智是「我要装插件 → 去插件管理」；另开一页会出现同一个插件在两个地方各显示一次。
2. 现有 `PluginPanel`（323 行）的分组列表、开关、删除、日志都能直接复用，只多一列「安装 / 更新」按钮。
3. 手机上少一层导航（长按 ☰ 已经够深了）。

```
插件管理页（mainView === 'plugins'）
┌──────────────────────────────────────────────────┐
│ 插件管理        [ 已安装 13 ] [ 发现 24 ]  [重新扫描] [返回] │
├──────────────────────────────────────────────────┤
│ 🔍 搜索           分类 全部▾   平台 全部▾          │
├──────────────────────────────────────────────────┤
│ 标签面板            工具 · 桌面+手机   [已安装 0.2.0] │
│   全库标签按篇数降序，点标签看该标签下的笔记          │
├──────────────────────────────────────────────────┤
│ 打卡 habit          工具 · 桌面+手机   [↑ 更新 0.3.0] │
│   四种频率 · 月历 · 连续天数                        │
├──────────────────────────────────────────────────┤
│ 记账 accounting     工具 · 手机        [安装 0.2.0]   │
│   通知自动记账 · 统计 · CSV 导入导出                 │
└──────────────────────────────────────────────────┘
```

**入口（前三个已经有了，不用动）**

| 入口 | 桌面 | 手机 |
|---|---|---|
| 菜单 | 右键 ☰ → 「插件管理」 | 长按 ☰ 600ms → 菜单 → 「插件管理」（或「⋯」按钮） |
| 命令面板 | `core.plugins` | 同左（菜单里也有「命令面板」） |
| 拖放（新增） | 把 `.znp` 拖到窗口 → 同一个安装确认框 | 不支持（SAF 限制） |
| 直达市场（新增，可选） | 命令 `core.market` → 打开插件页并切到「发现」tab | 同左 |

**安装流程（4 步）**

```
点「安装」
  → ① 确认框：名字 / 版本 / 作者 / 大小 / 来源 URL
       ⚠ 能力自述：「可读所有笔记 · 可发网络请求 · 可执行命令」
  → ② 下载（进度条）
  → ③ 校验：sha256 对不上 ⇒ 中止并报出哪一段不符；有 signature.json ⇒ 验签失败直接拒装
  → ④ 解包进全局根 → 自动重扫 → 跳到「已安装」并启用 → toast
```

第 ③ 步是关键：**下载失败、校验失败、验签失败，一律不落盘**（现在的 `install_znp` 是「覆盖写同名文件」，半截包会污染现有插件 —— 需要改成「先解到临时目录 → 全部成功再换目录」）。

**更新方式（三档，默认第二档）**

| 档 | 行为 | 用户能关吗 |
|---|---|---|
| 手动 | 顶部「检查更新」按钮 | — |
| **启动静默检查**（默认） | 24 小时最多一次，**只在新版本时给角标**，不下载、不安装 | ✅ 设置页开关 |
| 自动安装 | ❌ **不做**：插件能读任意文件、能 invoke 命令，换代码必须让人看见 | — |

升级交互 = 安装手势 + 一个 `↑ 更新 0.3.0` 的前缀。**不静默升级**这条要写进插件页的文案里。

### 4.5 开发者：怎么上传、怎么维护（2026-10-25 补）

分两种作者，流程完全不同。

#### A. 官方插件（作者 = 你）—— 目标是**零手工**

```
examples/tag-panel/            ← 源码，改了就是改了
        │  node scripts/pack-plugin.mjs tag-panel
        ▼
dist/tag-panel-0.2.0.znp       ← 目录 → 单文件 JSON + sha256 + 签名
        │  node scripts/gen-market.mjs
        ▼
market/index.json              ← 从 examples/*/manifest.json 自动生成，不手写
        │  git push / CI
        ▼
GitHub Release + raw 索引       ← 用户端读这个
```

| 步骤 | 谁做 | 频率 |
|---|---|---|
| 写插件 | 你，在 `examples/<id>/` | 随时 |
| 打包 + 签名 | `pack-plugin.mjs`（一条命令，或 CI） | 每次发版 |
| 生成索引 | `gen-market.mjs`，**跑进 verify 质量门**（索引与 examples 不一致 ⇒ 门红） | 每次提交 |
| 上传 | GitHub Actions：打 tag → 跑两个脚本 → 传 Release → 提交 index.json | 自动 |

**维护成本 ≈ 0**：索引不是人写的，是生成的。加一个插件 = 加一个目录。

#### B. 外部作者（将来开放）—— 索引里**不存版本号**

照 Obsidian 的做法，但补上它没有的签名：

1. 作者的仓库根放一个 **`market-entry.json`**（由 `pack-plugin.mjs` 自动生成，作者不用手写）：
   ```jsonc
   { "id": "xxx", "version": "0.3.0", "apiVersion": "^0.2.0",
     "url": "https://github.com/<user>/<repo>/releases/download/v0.3.0/xxx.znp",
     "sha256": "<包 sha256>", "sig": "<可选：对上面整段的签名>" }
   ```
2. 作者提 PR 到索引，**只加一行**：
   ```json
   { "id": "xxx", "name": "…", "author": "…", "repo": "user/repo",
     "entry": "https://raw.githubusercontent.com/user/repo/main/market-entry.json" }
   ```
3. 客户端：列表页读索引（含 `latest` 快照，CI 定时刷新）；**点安装时先 GET `entry` 拿真实最新**，再下载。

为什么这样设计：

| 设计 | 好处 |
|---|---|
| 索引不存版本号（只存 `entry`） | 作者发版**不用改索引**，也不会出现「索引说 0.3、实际 0.4」的漂移 |
| `latest` 快照 | 列表页一次请求就能显示版本，不用对每个插件发一次请求 |
| `market-entry.json` 由脚本生成 | 作者不需要理解格式，打包时自动产出 |
| 有 `sig` 字段 | 将来索引可信后可以「索引签名 + 包签名」双层，Obsidian 没有这个 |

#### 审核与维护

| 事项 | 做法 | 成本 |
|---|---|---|
| PR 审核 | **只审格式，不审代码**：CI 跑 `verify-market.mjs`（entry 可达、格式对、sha256 与包匹配、apiVersion 兼容） | 自动 |
| 代码审核 | ❌ 不做。内核本来就不为插件提供安全保证（架构原则 §4.1），假装审过反而危险 | — |
| 健康检查 | 每周 CI 跑一次全量，404 / sha256 不符 / 仓库归档 ⇒ 索引里标 `broken: true`，客户端显示「此插件已失效」 | 自动 |
| 下架 | 从索引删一行 + 客户端对已装插件不做任何事（用户装过的仍然能用） | 1 分钟 |
| 作者注销仓库 | 同「下架」；已装的插件因为`.znp` 已在本地，不受影响 | — |

> **备案**：这套设计只在「你自己发 + 少量外部作者」的规模下成立。真到几百个插件、恶意提交出现时，必须有人工审核队列 —— 那已经不是 `D-009` 的「不做服务端」能覆盖的范围了。本文不假装它能扛住那个规模。

## 5 安全叙事（必须诚实，不能包装）

架构原则 §4.1 的定论仍然有效：**内核不为插件提供任何安全保证**。插件能读任意文件、能发网络请求、能 invoke 六类命令。

所以市场**不是安全门**，它的准确定位是：

> **发现渠道 + 身份证明**：告诉你「有哪些」，以及「这个包装的时候确实是那个人发的、之后没被改过」。

能做的（成本都不高）：

| 措施 | 说明 | 成本 |
|---|---|---|
| 包签名 | 已有（Ed25519） | 0 |
| 索引签名 | `index.json` + 分离签名，防 CDN / 代理篡改。**如果索引放在你控制的仓库，风险等同仓库被盗**，可以先做「记录 sha256」不做签名 | 2 h |
| 安装前展示能力自述 | 已有（`.znp` 确认框会列 `capabilities`） | 0 |
| 首次启用警告 | 「这个插件可以读你的所有笔记」 | 0.5 h |
| 预置信任公钥 | 把市场公钥**编译进**应用（`trusted-keys.json` 内置一份），否则第一次装市场包必然验签失败 | 1 h |

**需要明确说清的一件事**：一旦把某个公钥内置进应用，**谁持有那个私钥，谁就能向所有用户推送任意代码**。这是本方案里最大的一处权力集中，应该写进 README 和插件页，不能藏。

**签名覆盖不全的问题（§3 #5）—— 扩还是不扩，差别到底在哪**

现在的 payload 是 `zn-plugin-v1|<id>|<version>|<入口文件 sha256>`，**只签入口**。`manifest.files` 里声明的 `lib/*.js` 一个都没签。

先看三条路径，风险完全不同：

| 路径 | 不扩签名会怎样 | 为什么 |
|---|---|---|
| **① 从市场装**（索引里有 `.znp` 整体 sha256） | ✅ **安全** | 索引的 sha256 覆盖**整个包**，改一个字节就比对不上、拒装。签名在这里只负责「是谁发的」，完整性由 sha256 兜住 |
| **② 手动分发**（微信发一个 `.znp`） | ❌ **有洞** | 攻击者拿你**公开的** `signature.json` + 入口文件，替换掉 `lib/x.js` 重新打包 ⇒ 入口 sha256 没变 ⇒ **验签通过、恶意代码落地** |
| **③ 装完之后被改** | ❌ **有洞** | 入口被改会被抓（重算 sha256 不符 ⇒ 拒载）；`lib/*.js` 被改**不会被发现** |

**现实数字（2026-10-25 实测）**：

- 37 个示例/预装插件里，**只有 1 个用 `manifest.files`**（`cjs-multi`，还是个示例）
- **有 `signature.json` 的插件：0 个** —— 签名机制在，但没有任何插件真的签过

所以成本差得非常悬殊：

| 时机 | 成本 |
|---|---|
| **现在扩** | 改 `signingPayload` 一处 + 更新测试与文档 = **1.5 小时**，零用户影响（没人签过名） |
| **以后扩** | 所有已分发并签过名的包**全部失效** —— 宿主重算 payload 对不上 ⇒ **拒载**，用户侧表现就是「插件突然加载失败」，必须同时发新版包 |

**已扩（rev173.142 · 2026-10-25 用户拍板「扩」）** —— 下面是最终落地形态：

```
zn-plugin-v2|<id>|<version>|<入口 sha256>|<path:sha256 按路径字典序，用 | 分隔>
```

- 没有 `files` 的插件末尾留空段：`zn-plugin-v2|tag-panel|0.2.0|<sha>|`
- 实测 `examples/cjs-multi`：`zn-plugin-v2|cjs-multi|0.1.0|<entry>|lib/counter.js:<sha>|lib/greet.js:<sha>`
  （manifest 里声明顺序是 greet → counter，payload 里按路径排序 ⇒ 与遍历顺序无关）
- **零兼容成本**：升级时实测 0 个插件带 `signature.json`，v1 直接作废
- 改动三处：`src/lib/plugin-signing.ts`（payload）· `scripts/sign.mjs`（同步）· `src/kernel/plugin-host.ts`（**先读 `manifest.files` 再验签**，读到的内容两处复用，不重复读盘）
- Rust 侧**没改**：`verify_plugin_signature` 只对 payload 字符串验签，不关心内容

**没纳入签名的**：`platforms` / `capabilities` / `name` 等 manifest 字段。

- `capabilities` 只是自述（架构原则 §4.1），签了也不能当权限用，反而给人"签过 = 安全"的错觉；
- `platforms` 被改的后果是「插件在另一平台显示不可用」，不构成代码注入；
- `id` / `version` 本来就在 payload 里，改了就失效。

如果以后要做「清单式审核」（capabilities 与实际调用比对），再把这些字段纳入，那时是一次格式升级（v3）。
