## 0 结论速览

1. **同步的难点不是搬文件，是「谁来判断冲突」。** 内核 10 条原语里**没有网络、没有二进制读写、没有库外静默写**（§3），
   插件今天做不到「自己把一个 `.md` PUT 到 WebDAV」，也读不了 PDF/图片的字节。
2. **最省的第一期不是做同步，是做「同步的体检与兜底」**：库放进用户自己的同步目录（OneDrive / Syncthing / 坚果云），
   插件负责 ① 发现外部改动 ② 判定「双端都改」 ③ 冲突留副本 ④ 状态页。**零内核改动，1–1.5 天**（方案 A）。
3. **真要在 App 内直连 WebDAV，必须先给内核一条走 Rust 的 HTTP 通道**（`tauri-plugin-http` 的 fetch
   在 Rust 侧执行，**不受 CORS 约束**，官方原文见 §4.5）；Rust 侧有现成 WebDAV 库 `reqwest_dav`（§4.9），
   不用自己写协议。**含「无感同步」（近实时）总成本约 3 天**（方案 B）。
   「无感」的准确边界：**前台 2–7 秒**；后台 / 锁屏收不到（Android 挂起 WebView 定时器），切回即追平。
4. **Git 同步只适合桌面**：手机端 isomorphic-git 被作者自己标为 "very unstable"（§4.4），不做主线（方案 C）。
5. 需求 §2.5 里「扫码配置 / 大文件按需同步」**本期不做**；「**实时自动同步**」**确认要做** ——
   用户 2026-10-24 明确要「无感同步」，落地方式见 §5 方案 B 的近实时设计（前台 2–7 秒）。
6. **GitHub 上的成熟实现（§4.7–4.10）指向同一条路**：元数据放本地、远端只存文件、冲突优先保留两份。
   而且 **Obsidian 自己也没能用浏览器 API 绕开 CORS** —— 它加了宿主级 `requestUrl`；Tauri 的等价物就是 `tauri-plugin-http`。
   ⇒ 任何「在 WebView 里直连 WebDAV」的想法，先过这一关。

## 1 需求原文与历史决策

需求规格 §2.5（`docs/archive/Markdown 笔记应用需求规格 v1.0.md:208-228`）：

- 实时自动同步
- MVP 支持：**WebDAV** + **本地文件夹同步**（用户可配 Syncthing / OneDrive / 网盘等）
- 扫码配置后置
- 冲突：正常以最新为准；**双端离线修改时生成冲突副本**（不弹窗阻塞），副本按平台分文件夹

`D-002`（2026-10-17，accepted）当时结论是「不做账号 / 服务器 / 云同步，同步交给用户自己的网盘」，
重议条件 =「多设备冲突成为真实痛点，且明确接受『冲突文件』语义」。
**本次正是该重议**：只做客户端侧的同步能力，不做服务端、不做账号。

## 3 三个技术缺口（方案边界由它们决定）

1. **网络**：WebDAV 的 `PROPFIND`/`PUT` 不是简单请求，必然触发 CORS preflight（`OPTIONS`）；
   服务器不回 CORS 头就一律失败，插件侧只能看到 `TypeError: Failed to fetch`，**分不清是 CORS、断网还是 401**
   （2026-10-12 踩过一次，见 `插件能力盘点` 的更正段）。⇒ 要么走 Rust，要么不直连。
2. **二进制**：同步必须覆盖图片附件与 PDF/EPUB；`fs` 只有文本。`copy` 能复制但不能读写内容（做不了「下载字节 → 写文件」）。
3. **库外静默写**：把笔记镜像到另一个目录需要静默写库外，现有 `host.saveFile` 每写一个文件弹一次对话框。

## 4 同类做法（一手来源）

### 4.1 Joplin —— 抽象驱动 + item 级 + updated_time 判据
- 同步目标：Joplin Cloud / Nextcloud / S3 / WebDAV / Dropbox / OneDrive / 本地文件系统，
  统一成「类文件系统」驱动（read / write / delete / list），换服务只换驱动。
- 流程是 **item 级**：改动后数秒内上传该 item，下载按固定间隔（几分钟）轮询 —— **冲突多发生在下载间隔内**。
- 冲突判据：item 的 `updated_time`。默认 `sync.autoMergeConflicts` 会用 base/local/remote 三路行级合并；
  合不了才落冲突副本。
- 冲突副本：新建一条 note（**标题不变**，新 id，标 `is_conflict=1` + `conflict_original_id`），
  远端版本替换本地。
- 删除：`deleted_time` 软删除 + 删除记录传播。
- 来源：https://joplinapp.org/help/apps/sync/ · https://joplinapp.org/help/dev/spec/sync · https://joplinapp.org/help/dev/spec/conflict_auto_merge

### 4.2 Obsidian Sync —— 文件级、默认自动合并、冲突文件是可选项
- 文件级同步，按文件大小给上限（Standard 5 MB / Plus 200 MB）。
- 冲突：Markdown 默认 **diff-match-patch 自动合并**；其它文件 last-modified-wins；设置文件按键合并。
- 1.9.7+ 可选「Create conflict file」，命名 `笔记名 (Conflicted copy 设备名 YYYYMMDDHHMM).md`。
- E2EE 默认（AES-256-GCM / scrypt），订阅制 $4/用户/月。
- 来源：https://obsidian.md/help/sync/troubleshoot · https://obsidian.md/help/sync/security · https://obsidian.md/help/sync/plans

### 4.3 Syncthing —— 块级传输 + 文件名后缀
- 文件切块（128 KiB–16 MiB），每块 SHA256，只传变化的块。
- 冲突条件：同文件两台设备都改且内容不同 ⇒ **mtime 较旧的那个**改名为
  `<文件名>.sync-conflict-<日期>-<时间>-<设备>.<扩展名>`；mtime 相同则 device ID 较大者被标冲突。
- 冲突副本按普通文件继续传播；删除 vs 修改冲突时，删除赢也会把文件改名成冲突副本。
- 来源：https://docs.syncthing.net/users/syncing.html

### 4.4 obsidian-git —— Git 冲突靠编辑器 UI
- 定时 commit + pull + push；启动先 pull。
- 同文件两端修改 = 真 Git merge 冲突，插件只做 UI（keep ours / theirs / both），不做语义合并。
- **移动端用 isomorphic-git，作者自述 "very unstable"**，无 SSH、无 rebase、有内存限制。
- 来源：https://github.com/Vinzent03/obsidian-git

### 4.5 Tauri 2 的 HTTP 客户端 —— 绕 CORS 的正路
- `@tauri-apps/plugin-http` 的 `fetch` **在 Rust 侧（reqwest）执行**。官方 API 文档原文：
  > "The request is performed by the Rust backend instead of the webview, so **it is not subject to CORS**,
  > but the URL must be allowed by the plugin scope."
- 平台支持：Windows / Linux / macOS / **Android** / iOS 全绿；要求 Rust ≥ 1.90；权限在 capabilities 里用
  `http:default` + URL glob 白名单声明；CSP 也要放行对应 host。
- 维护者在 issue 里的一句话佐证：「using Tauri's http api may help since its executed on the rust side where cors isn't a thing」。
- 来源：https://v2.tauri.app/reference/javascript/http/ · https://github.com/tauri-apps/tauri/issues/11260

### 4.6 WebDAV 直连在浏览器里的现实
- `PROPFIND` 不是简单方法（简单方法只有 GET/HEAD/POST）⇒ **必触发 preflight**；`PUT` 带自定义头也 preflight。
- Nextcloud issue #3131（2017 开、至今 open）：*"Currently this is not possible as the necessary CORS headers are not set."*
- 坚果云官方帮助中心没有 CORS 相关说明（未找到一手来源证明其返回 ACAO）。
- 来源：https://developer.mozilla.org/en-US/docs/Glossary/Preflight_request · https://github.com/nextcloud/server/issues/3131

### 4.7 remotely-save（Obsidian 社区插件 · 最贴近的一份实现）
- 支持 14 种远端：S3 兼容 / Dropbox / OneDrive / **WebDAV**（Nextcloud / 群晖 / **坚果云** / AList / InfiniCloud …）/ Webdis / GDrive / Box / pCloud / Yandex / Koofr / Azure Blob。
- 算法 v3（`docs/sync_algorithm/v3/intro.md`）：**不再在远端存元数据**（"no remote meta data any more"），
  改成**本地数据库 + 远端纯文件**；增量 push / 增量 pull；删除用「真删除状态计算」；同步前按阈值警告。
- 冲突策略：免费版只能 **keep newer / keep larger**（二选一）；"keep both and rename" 与"显示警告"**未实现**；
  付费 PRO 才有「小 md 合并 / 大文件复制成副本」。
- **隐藏文件（`.` 开头）默认不同步**；定时同步**只在 Obsidian 打开时**有效（浏览器环境限制）。
- 凭据放插件目录的 `data.json`（**明文**，作者建议手工加 `.gitignore`）。
- CORS：新版 Obsidian 的 `requestUrl` 让插件**完全绕开 CORS**；老版本要服务端配 `Access-Control-Allow-Origin`。
- 来源：https://github.com/remotely-save/remotely-save · https://raw.githubusercontent.com/remotely-save/remotely-save/master/docs/sync_algorithm/v3/intro.md · https://raw.githubusercontent.com/remotely-save/remotely-save/master/docs/browser_env_cors.md

### 4.8 obsidian-livesync（Self-hosted LiveSync）
- 载体：CouchDB / S3 兼容对象存储 / **WebRTC P2P**（仍需 signalling relay）。
- **块级同步**（chunk + metadata），增量；「自动合并简单冲突」；E2EE；隐藏文件同步是单独开关。
- 明确要求「不要和别的同步方案同时开」；需要自己维护服务端（CouchDB / MinIO）。
- 对我们：需要服务端的路子与 `D-002` 冲突；但「块级 + 本地索引」仍是同一思路。
- 来源：https://github.com/vrtmrz/obsidian-livesync

### 4.9 Rust 侧有现成的 WebDAV 客户端（方案 B 的实现前提）
- `reqwest_dav`（Rust，tokio + reqwest）：Basic / Digest 认证，GET / PUT / MV / CP / DELETE / MKCOL / LIST 全有。
- **不必自己写 WebDAV 协议与 XML 解析**，方案 B 的 Rust 侧从「0.5–1 天」降到「半天量级」。
- 验收时还可以用同作者风格的轻量 WebDAV 服务（`dufs`，Rust 单文件）或 `rclone serve webdav` 当测试靶子。
- 来源：https://github.com/niuhuan/reqwest_dav

### 4.10 四条实现给同一个结论
| 实现 | 元数据放哪 | 冲突处理 | 怎么绕 CORS |
|---|---|---|---|
| Joplin | 每条 note 的 `updated_time` | 三路自动合并 → 合不了才落冲突副本 | 原生（Rust/Node） |
| Obsidian Sync | 文件 mtime/版本 | 默认自动合并；可开冲突文件 | 官方云端 |
| remotely-save | **本地数据库，远端只存文件** | keep newer / larger（PRO 才合并） | **宿主 `requestUrl`** |
| obsidian-livesync | 本地索引 + 远端 chunk | 自动合并简单冲突 | 宿主通道 |

⇒ 三条共识：**① 元数据放本地；② 冲突时优先保留两份，且尽量自动合并简单的；③ 浏览器环境里必须有宿主提供的绕 CORS 通道。**

### 4.11 跨领域借鉴：五种同步模型（不限于笔记类）

| 项目 | 领域 | 同步单位 | 冲突判定 | 冲突产物 |
|---|---|---|---|---|
| **rclone bisync** | 通用文件同步 CLI | 文件 | 两侧都 new/changed（相对上次运行）**且内容当前不同** | 默认**两边都改名**：`file.txt.conflict1` / `.conflict2`，两份都复制到对侧 |
| **Syncthing** | P2P 文件同步 | 块（128 KiB–16 MiB，SHA256） | 同文件两侧改且内容不同 | mtime 较旧者改名 `.sync-conflict-<日期>-<时间>-<设备>` |
| **Git** | 版本控制 | 内容 DAG / 行 | 同一区域两侧都改 | 索引记三份：**base（共同祖先）/ ours / theirs**，工作区写 `<<< === >>>` |
| **Joplin** | 笔记 | item | `updated_time` | 有 base 时三路合并，合不了才落冲突副本 |
| **remotely-save** | 笔记（Obsidian） | 文件 | 无 base，只能 newer / larger | 免费版**直接选一个赢家，不产生副本** |

**关键分野：有没有 base（共同祖先）。**
- Git / Joplin 有 base ⇒ 能做三方合并，冲突时还能自动合掉不重叠的改动。
- rclone / Syncthing / remotely-save 没有 base ⇒ 只能判断「两侧都改过」，然后**保留两份**或**选一个**。

**ZeroNote 属于第二类。** `.md` 没有版本历史，除非把 `history` 插件的快照当 base ——
那是二期的事（成本高，且 history 只在关闭/切换时存）。

**rclone bisync 是这五者里工程细节最完整的一份**，可直接抄的五条：

1. **上次同步快照**：每次跑完存一份 listing（`~/.cache/rclone/bisync/*.lst`），下次只对比快照 → 现状。
   我们对应：`store` 里的 `baseline: { path → { hash, mtime, savedAt } }`。
2. **冲突保留两份 + 可读后缀**：默认 `--conflict-resolve none` ⇒ 两份都改名（`.conflict1`/`.conflict2`）并各复制到对侧；
   可加日期变量（`{DateOnly}-conflict`）。
3. **安全阀**：`--max-delete 50%` —— 一次删除超过 50% 文件就中止，防止「同步工具误判全删」把两边清空。
   **这条对我们也必须抄**（同步插件最怕的是一次误操作删光整个库）。
4. **锁文件**：防两个同步进程同时跑；`--max-lock` 让崩溃留下的锁自动过期。
5. **过滤器变更要检测**：rclone 把过滤器文件的 MD5 存下来，一变更就强制 `--resync` ——
   因为规则变了会让一批文件从 listing 里“消失”，被误判成删除。我们的 `.zn/`、`冲突/` 排除规则同理。

**不建议抄的：**
- **块级同步**（Syncthing / Seafile 式）：笔记都是几 KB 的小文件，块级收益近乎零，却要维护索引库与块表。
- **CRDT**（Yjs / Automerge 式）：要改数据模型（把 `.md` 变成 CRDT 文档），与「数据就是你的文件」正面冲突。
- **三方合并**（Git / Joplin 式）：需要 base，我们只有 history 快照可借；放到二期。

> 来源：https://rclone.org/bisync/ · https://docs.syncthing.net/users/syncing.html · https://git-scm.com/docs/git-merge ·
> https://joplinapp.org/help/dev/spec/conflict_auto_merge · https://github.com/remotely-save/remotely-save

### 4.12 NoteGen（`codexu/note-gen`）—— 8 种后端，Git 类走 **REST API** 不是 git 协议

官方文档（notegen.top）列的同步方式：GitHub / GitLab / Gitee / Gitea、S3、WebDAV、
OneDrive / iCloud Drive（云盘文件夹）、NoteGen 自托管（实验性）。

**核实（源码依赖）**：`src-tauri/Cargo.toml` **没有任何 git 库**（无 `git2`、无 `gix`），
只有 `tauri-plugin-http`、`reqwest`、`reqwest_dav`
⇒ **Git 类同步是通过各平台 REST API 做的（Contents API），不是 git clone/push**。
旁证：文档要求的 GitHub 权限是「Fine-grained PAT，Contents 读写」+「创建仓库时 Administration 读写」——
创建仓库只能走 REST `POST /user/repos`，git 协议没有这个动作。

**限流**：GitHub 认证用户 REST 限额 5000 次/小时。5 秒轮询 manifest ≈ 12 次/分钟，够用；
只要做增量（不比整棵树）就不会打满。

**它的 SHA 就是乐观锁**：GitHub Contents API 写文件必须带当前 `sha`，对不上就拒
⇒ 与我们要做的 `If-Match` 等价，Git 后端反而**省掉**自己实现锁的工作。

**同步对象分两类**（值得抄）：
- Markdown 与资源：**文件级**上传/拉取
- 记录、标签、聊天、画布、设置：**结构化数据**，单独检测跨设备冲突

**冲突只有三选项**：合并两边内容 / 远程覆盖本机 / 本机覆盖远程 —— **不保留副本**（后两者明确写「会丢弃一侧」）。

**其他可抄的**：「打开文件时自动拉取」「切换文件时自动拉取」（把冲突窗口压小）；
以及警告「不要让两种同步工具同时管理同一个工作区」。

> 来源：https://notegen.top/cn/docs/settings/sync · https://notegen.top/cn/docs/guides/multi-device-sync ·
> https://github.com/codexu/note-gen（`src-tauri/Cargo.toml`）

## 5 候选方案

### 5.0 多后端抽象（用户 2026-10-24 定：仿 NoteGen，做多种方式让用户自己选）

引擎只依赖接口，各家实现各自的后端：

```ts
interface SyncBackend {
  id: 'webdav' | 's3' | 'github' | 'local-folder'
  label: string
  test(): Promise<void>                            // 连接测试
  list(prefix): Promise<RemoteFile[]>              // path / size / mtime / etag
  get(path): Promise<string | Uint8Array>
  put(path, content, { ifMatch? }): Promise<{ etag }>
  delete(path): Promise<void>
}
```

| 后端 | 可行性 | 实现要点 | 成本 |
|---|---|---|---|
| **WebDAV** | ✅ 最通用 | Rust `reqwest_dav`（Basic/Digest）；`If-Match` 自己实现 | 0.5 天 |
| **本地文件夹** | ✅ 零网络 | 库本身在同步目录里，插件只做冲突兜底（= 方案 A 的形态） | 0.5 天 |
| **S3 兼容** | ✅ | AWS SigV4 签名（约 100 行，或改用 crate） | 1 天 |
| **Git 类**（GitHub/Gitee/GitLab/Gitea） | ⚠️ 可行但别扭 | REST Contents API；**SHA 自带乐观锁**；限流 5000 次/小时 | 0.75 天 |
| 自托管（NoteGen 式） | ❌ | 等于做服务端，违背 `D-002` | — |

**分期**：一期 = 引擎 + WebDAV + 本地文件夹（**3.5 天**）；二期 = S3（+1 天）；三期 = Git 类（+0.75 天）。全做约 **5.5 天**。

**凭据**：一期存 `store`（明文 JSON，设置页明确警告）；二期接系统钥匙串（Rust `keyring` crate）。
⏳ **待用户点头**：一期先用明文。

### 方案 A（备选，满足不了「无感」）：同步体检 + 冲突兜底 `sync-guard`
**不搬运文件**：库放进用户自己的同步目录，搬运交给 OneDrive / Syncthing / 坚果云。
插件只做三件事：发现外部改动、判定双端都改、冲突留副本。

- 数据：`store` 里 `baseline: { [path]: { hash, mtime, savedAt } }` + `device`（windows/android）
- 判定：
  1. `note:saved` ⇒ 更新 `baseline[path] = { hash, mtime, savedAt: now }`
  2. `note:changed`（外部改动，内核已过滤自写）⇒ 该 path 在基线里且 hash 变了：
     - `savedAt` ≤ 基线时间 ⇒ 只是别处更新 ⇒ 接受，刷新基线
     - `savedAt` > 基线时间 ⇒ **双端都改** ⇒ 冲突
  3. 冲突 ⇒ 从 `.zn/history/` 取该篇最近一份「冲突前快照」，`fs.copy` 成
     `冲突/<windows|android>/<YYYY-MM-DD HHmm>-<文件名>`；toast + 面板记录（不弹窗阻塞）
  4. 删除 vs 修改：外部删、本地改过 ⇒ 本地版留成冲突副本；本地删、外部改 ⇒ 恢复外部版
- 面板 `sync.status`（主区标签）：最近外部改动时间 · 冲突列表（点击跳转）· `.zn/` 是否被同步工具同步
  （若收到 `.zn/` 内的外部改动事件 ⇒ 警告「同步工具正在同步私有目录」）· 同步建议（排除 `.zn/`、`_shots/`）
- **安全阀（抄 rclone 的 `--max-delete`）**：一次同步若要覆盖/删除超过 20% 的笔记 ⇒ 中止并亮红灯，
  不自动执行；用户点「仍然继续」才放行
- 能力：`fs` `store` `event` `view` `command` `host`（可选 `service` 调 `history`）
- **成本：1–1.5 天**（插件一个，不动内核）
- 验收：造两个库副本模拟两端 → 改同一篇 → 手动覆盖触发 → `冲突/windows/...` 出现且内容 = 本地版 ·
  状态页数字对 · 单测覆盖判定函数（四类场景）· 手机端同一套（3 秒轮询）
- 局限：同步本身依赖第三方工具；手机要装 Syncthing（SAF 选目录有摩擦）；冲突是「事后发现」

### 方案 B（推荐做第一期）：WebDAV 直连 `sync-webdav` · 目标「无感同步」
- 前提：内核先有一条**走 Rust 的 HTTP 通道**。三种实现，推荐 B-1：
  - **B-1**：内核加 `host.http()` 原语（契约 v0.3），内部调 `plugin:http|fetch`；
    scope 用 capabilities 的 `http:default` + 用户配置里声明的 DAV 域名（运行时拼不进静态 capability ⇒
    退一步允许 `https://*`，在设置页写明「同步插件可访问任意 https 地址」）
  - B-2：内核自己写一条 Rust `http_request` 命令（reqwest 直连，scope 自控）
  - B-3：插件直接 `__TAURI_INTERNALS__.invoke('plugin:http|fetch')`（**不推荐**：绕过契约，等于给所有插件开后门）
- 同时补二进制：`fs.readBytes` / `fs.writeBytes`（或让 `host.http` 直接支持 base64）
- **近实时设计**（「无感」的实现方式）：
  1. **manifest 文件**：远端存 `_sync/manifest.json`（每个文件的 hash + 时间）。对端只拉这一个几 KB 的文件，
     就知道哪些变了 —— 比 `PROPFIND` 整棵树便宜得多
  2. **保存即推**：`note:saved` → 节流 1.5 秒 → `PUT` 该篇 + 更新 manifest
  3. **短轮询**：前台每 5 秒 `GET manifest`（带 `If-None-Match`，没变返回 304，流量≈0）
  4. **`If-Match` 乐观锁**：`PUT` 带上次下载的 ETag；远端在你编辑期间变了 ⇒ **412** ⇒ 走冲突流程，
     不会静默覆盖
  5. **打开 / 切换文件时先拉一次**（NoteGen 的做法）：让用户永远在最新内容上改
  6. **前后台**：`visibilitychange` 停 / 启轮询；切回前台立即全量拉一次
  7. 手机后台收不到（系统挂起定时器）—— 已知边界，见 §8 第 5 条
- 插件：WebDAV 客户端 —— **Rust 侧用现成 crate `reqwest_dav`**（Basic/Digest + LIST/GET/PUT/MV/DELETE/MKCOL，
  见 §4.9），不用自己写协议与 XML 解析 · 凭据存 `store`（**明文风险要写给用户**）或系统钥匙串
  （Rust 侧 `keyring` crate）· 冲突副本复用 §6 的判定
- **成本：约 3 天**
  | 阶段 | 天数 |
  |---|---|
  | 内核 HTTP 原语 + capabilities | 0.5 |
  | manifest 协议 + 增量推送/拉取 | 1 |
  | 冲突检测（If-Match + 基线）+ 冲突副本 | 0.5 |
  | 前后台生命周期 + 打开时拉取 | 0.5 |
  | 测试与真机验收 | 0.5 |
- 风险：凭据安全 · 坚果云限流（免费 600 次/30min；5 秒轮询每分钟 12 次 ≈ 24 分钟用掉 300 次）·
  大文件超时 · 各家 WebDAV 行为差异 · 手机后台收不到
- 验收：本地 Nextcloud / dufs 沙箱两端改同一篇 → 冲突副本 · 5 MB 附件往返 · 断网重试 · Android 真机
  **延迟实测**：A 端保存 → B 端出现（目标 ≤ 7 秒）

### 方案 C（不推荐主线）：Git 同步
- 桌面：Rust 调外部 `git`（或加 `proc` 能力），定时 commit+push；冲突 = Git merge。
- 手机：isomorphic-git 作者自述 very unstable ⇒ 不做。
- **成本 1.5 天（桌面 only）**，收益不大。

### 方案 D（不做）：自建服务端 / 账号 / E2EE
违背 `D-002` 与产品定位（无服务器、数据就是文件）。E2EE 只在 Obsidian 那种「有云端」的场景才有意义。

## 6 冲突语义（这是 D-002 的卡点，必须先定）

### 6.1 一期：留两份（不需要 base）

| 场景 | 判定 | 处理 |
|---|---|---|
| 只有本地改 | `savedAt` 更新、无外部事件 | 无动作 |
| 只有外部改 | 外部事件 + 本地 `savedAt` ≤ 基线 | 接受，刷新基线 |
| **双端都改** | 外部事件 + 本地 `savedAt` > 基线 | 原路径保留外部版；本地版（取 `.zn/history/` 最近快照）写到 `.zn/conflicts/<平台>/<时间>-<文件名>`；toast + 面板 |
| 外部删 / 本地改 | 外部 delete + 本地 `savedAt` > 基线 | 本地版写成冲突副本（恢复一份） |
| 本地删 / 外部改 | 本地 delete 在外部改动后 | 接受外部版（恢复文件） |
| 改名 | path 变化 | 视为 delete + create（不跟 rename，成本不值） |

**冲突副本位置已定：`.zn/conflicts/<平台>/`**（库内 `冲突/` 会被第三方同步工具再传出去，Syncthing 官方明确说冲突文件会当普通文件继续传播 ⇒ 冲突会雪球）。

### 6.2 二期：三方合并（base 来自 history）

> ✅ **已实现（rev173.115，`sync-webdav` 后端）**。落地时与本节的四处差异，均有意为之：
> 1. **同步点用固定名** `<库>/.zn/history/<hash32>/base.sync.md`（本节原写 `<时间戳>.sync.md`）——
>    固定名只有一份 ⇒ 不需要「精简例外」、也不会把历史列表灌满（`parseSnapshotName` 不认它）。
> 2. **`history` 触发没改防抖**：仍按需求 §11「关闭 / 切换时存」。三方合并只需要**同步点**
>    （由同步插件在每次成功推 / 拉后覆盖写），不需要更细的历史粒度；改成 5 秒防抖会让快照量
>    涨一个数量级（7 天内全留）。
> 3. **合并实现走内核内置服务 `kernel.merge`**（不是插件 import `src/lib/merge3.ts` —— 插件宿主
>    只给原语，import 不进去）。同一份实现，插件与内核写盘前合并语义一致。
> 4. **`sync-folder` 后端暂未接**：它的冲突双方是「影子副本 vs 磁盘」，接入前要先处理
>    「自己写盘触发 `note:saved` ⇒ pending 自环」，留到下一 rev。
>
> 判据比本节更保守：**只有完全合上（`conflicts === 0`）才自动合**；有一处真冲突就退回本节 6.1
> 的「留两份」，不自动选边（自动选边会让用户以为已经合好了）。

**为什么要 base**：Git 的三方合并之所以能自动合掉不重叠的改动，全靠「共同祖先」。没有 base 只能二选一或留两份。

**base 从哪来**：**复用 history**，不另建一套存储。

```
.zn/history/<hash32(路径)>/
  2026-10-24T19-01-12.md          ← 普通快照（保存防抖 5 秒 / 关闭 / 切换）
  2026-10-24T19-05-33.sync.md     ← 同步点快照（sync 调用 history 打的标记）
  index.json                      ← 每篇：最近 sync 点、上次同步 hash
```

**history 要改三处**：

1. **触发改成防抖**：保存后 5 秒内无新保存 ⇒ 存一份。连续写一小时约 10–30 份（不是 4500 份）。
2. **加 `service`**（约 30 行）：
   ```js
   service.provide('history', {
     snapshot(path, content, { tag }),  // tag: 'sync' ⇒ 文件名带 .sync
     findBase(path),                   // 返回最近一个 .sync 快照
   })
   ```
3. **精简规则加一条例外**：最近一个 `.sync` 快照**永不淘汰**（哪怕它是 30 天前）。
   不加这条，长期没同步的笔记第一次同步时找不到 base，三方合并退化成留两份。

**sync 的改动**：
- 每次推送成功后调 `history.snapshot(path, content, { tag: 'sync' })`
- 冲突时 `history.findBase(path)` 拿 base，`lib/merge3.ts` 做三方合并
- 能合 ⇒ 自动合并 + toast「已合并 N 处」；合不了 ⇒ 只在冲突段落留两份

**降级**：sync 启动时检查 `history` service 在不在。
- 在 ⇒ 三方合并
- 不在（用户禁用 history）⇒ 退回 6.1 的「留两份」，**只是体验差，不丢数据**

**顺带的好处**：历史版本时间线能标出同步点（`19:05 ⟳ 同步到云`），用户回滚时知道哪一版已经同步出去了。
